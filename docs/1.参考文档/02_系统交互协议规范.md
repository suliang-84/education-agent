## 1. 文档说明

### 1.1 为何需要本文档

各模块规格说明书独立定义了各自的交互逻辑，历次发现并解决的设计冲突如下：

| 冲突类别 | 具体问题 | 严重程度 | 状态 |
|----------|----------|----------|------|
| 首页导航缺失 | 登录成功后跳转至哪个模块、Tab顺序未定义 | 🔴 阻断 | ✅ §2 |
| 模块主辅矛盾 | 03模块（题目驱动）与04模块（对话驱动）均主张自己是主线 | 🔴 阻断 | ✅ §4 |
| AI触发冲突 | 答错后 RAG 与助教对话同时触发，优先级未定义 | 🔴 阻断 | ✅ §5 |
| 五力阈值不一致 | "薄弱五力"在03模块为 <65分，在04模块为 <50分 | 🟠 体验影响 | ✅ §7 |
| 前置依赖矛盾 | 03模块强制五力测试，04模块允许降级 | 🟠 体验影响 | ✅ §8 |
| Token计算歧义 | 两模块Token上限数值含义不清 | 🟠 体验影响 | ✅ §5 |
| 数据类型不对齐 | 协议字段类型（VARCHAR/DATETIME）与PostgreSQL DDL不一致 | 🟠 实现风险 | ✅ §6（v2.0修正）|
| 缺少异步任务协议 | Celery队列分配、任务路由、重试策略未定义 | 🟠 实现风险 | ✅ §10（v2.0新增）|
| 缺少跨模块API契约 | 模块间内部调用方式未统一 | 🟠 实现风险 | ✅ §9（v2.0新增）|
| 安全标准散落 | 密码/手机号加密、JWT规格未统一 | 🔴 安全风险 | ✅ §11（v2.0新增）|

## 3. 用户旅程全链路

### 3.1 完整学习闭环

```
Phase 1 入门
──────────────────────────────────────────────────────────
POST /api/v1/auth/wx-login (微信授权)
POST /api/v1/auth/bind-phone (手机号绑定，可选)
   ↓
Phase 2 诊断
──────────────────────────────────────────────────────────
GET  /api/v1/test/questions (获取20道固定测试题)
POST /api/v1/test/answer    (逐题提交，支持中断恢复)
POST /api/v1/test/complete  (完成测试 → 同步触发评分 ≤3s)
GET  /api/v1/test/result/{session_id} (获取三层画像)
   ↓ 写入 five_power_profiles (is_latest=true)
   ↓ Celery Queue-E: AI个性化分析文字（异步）
Phase 3 学习（高频，每日）
──────────────────────────────────────────────────────────
[路径A：主动训练 Tab 1]
  GET  /api/v1/knowledge-points?grade=G9&subject=math
  POST /api/v1/training/session   (创建会话，返回5题题卷)
  POST /api/v1/training/answer    (逐题提交)
     ├── 答对 → 静默，proactive_count 不变
     └── 答错 → Celery Queue-C: RAG生成（≤8s，超时降级）
              → 连续答错≥2次且满足5条件 → 04模块悬浮介入
  POST /api/v1/training/complete  (训练结束)
     └── Celery Queue-P: 训练画像异步更新（≤5min）

[路径B：AI陪伴 Tab 2]
  POST /api/v1/assistant/session  (创建对话会话)
  POST /api/v1/assistant/message  (发送消息，AI启发响应)
     └── AI判断需要实战检验 → POST /api/v1/training/mini-session (2~3题微训练)
  PATCH /api/v1/assistant/message/{id}/rate (消息点赞/踩)

Phase 4 成长闭环
──────────────────────────────────────────────────────────
GET /api/v1/profile/history    (五力历史曲线)
POST /api/v1/test/start        (重测，间隔≥30天)
   ↓ 新画像与历史对比 → 展示成长
```

## 4. 模块主辅关系与职责边界

### 4.1 双轨并行协作模式

```
┌─────────────────────────────────────────────────────┐
│                   学习双轨                            │
│                                                     │
│  学生主动发起              AI感知后发起               │
│                                                     │
│  ┌──────────────────┐   ┌──────────────────────┐   │
│  │  03 个性化训练    │   │    04 智能助教         │   │
│  │  training_service│   │  assistant_service    │   │
│  │                  │   │                      │   │
│  │ "我要练这个点"    │   │ "我有个问题想问"      │   │
│  │ 结构化做题        │   │ AI 启发引导           │   │
│  │ RAG 解法层       │   │ 苏格拉底认知层        │   │
│  │ 训练画像更新      │   │ 策略自适应            │   │
│  └────────┬─────────┘   └─────────┬────────────┘   │
│           │ 答错/困境时              │ 推荐实战时     │
│           └──────────↔─────────────┘               │
└─────────────────────────────────────────────────────┘
```

**协作模式：并行双轨 + 互相调度，非主从关系。**

### 4.2 职责边界（不可越界）

**03_个性化AI训练 — 负责：**

| 职责 | 说明 | 对应服务方法 |
|------|------|-------------|
| 结构化选题 | 按五力权重从题库精准出题 | `training_service.create_session()` |
| 答错RAG指导 | 结构化解法框架（禁止苏格拉底风格） | `rag_service.generate_hint()` |
| 错题记录生产 | 写入 `wrong_answer_records`（review_status=unreview）| `training_service.record_wrong_answer()` |
| 训练画像更新 | 异步 EWMA 更新 `five_power_training_profiles` | Celery Queue-P |

**03模块不负责：** 多轮对话、启发策略切换、情感支持、`ai_student_strategy_profiles` 维护。

**04_智能助教 — 负责：**

| 职责 | 说明 | 对应服务方法 |
|------|------|-------------|
| 学习陪伴 | 感知困难，主动/被动介入 | `assistant_service.decide_proactive()` |
| 多维启发 | 9种策略，自动切换，苏格拉底式 | `assistant_service.select_strategy()` |
| 策略档案维护 | `ai_student_strategy_profiles` EWMA 更新 | 会话结束后异步 |
| 错题复盘 | 消费 `wrong_answer_records`（只读+状态更新） | `assistant_service.start_review()` |
| 微训练调度 | 调用03模块 mini-session 接口 | `training_service.create_mini_session()` |

**04模块不负责：** 大规模训练会话、题库管理、`five_power_training_profiles` 写入。

### 4.3 功能重叠处理规则

| 功能 | 裁决 |
|------|------|
| 错题复盘 | **两者互补递进**：03提供结构化解法（RAG），04提供认知启发（对话）。先看RAG，仍困惑则点击"与AI深入讨论"进入04 |

| Token消耗 | 各模块独立控制预算，共享 `ai_token_usage_log` 记录（见§5）|

## 5. AI调用协议

### 5.1 两类调用的角色定义

| 类型 | 模块 | 触发方 | 风格 | 输出限制 | 禁区 |
|------|------|--------|------|----------|------|
| **RAG解法指导** | 03_训练 | 系统自动（答错后） | 直接、结构化 | ≤200字 | 禁止苏格拉底提问（"你觉得…""想想看…"）|
| **对话启发引导** | 04_助教 | 学生提问/AI主动 | 苏格拉底式 | ≤400字 | 禁止直接给出解题步骤 |

### 5.2 同一答题事件的 AI 触发流程

```
学生提交答案
      │
      ├── 答对 → 完全沉默，不触发任何AI调用
      │
      └── 答错
           │
           ├── Step 1：Queue-C（RAG，P0，必然发生）
           │    T=0：   写入 training_answer_records，异步入队 Queue-C
           │    T=0+200ms：前端展示骨架屏"🤖 AI正在生成解题思路…"
           │    T=3s：  骨架屏加进度条
           │    T=8s：  RAG超时 → 降级展示（见§8.2）
           │    T=完成： 替换骨架屏，展示"查看解题思路"按钮（蓝色样式）
           │
           └── Step 2：04模块介入判断（P1，条件触发）
                满足 ALL 五个条件时触发：
                ① 同知识点连续答错 ≥ 2 次
                ② 当前学生会话 silence_mode = FALSE
                ③ 当前训练会话 proactive_count < 3
                ④ 距上次 RAG 生成完成 ≥ 90 秒
                ⑤ 本次 RAG 未超时或失败
                   ↓ 触发：创建/更新 ai_chat_sessions，前端展示悬浮条
                   ↓ 不触发：等待学生主动发起对话
```

### 5.3 Token 统一计费规范

#### 5.3.1 术语统一

| 术语 | 定义 |
|------|------|
| Prompt Tokens | 发送给 AI 的全部内容（系统Prompt + 用户输入 + 检索结果） |
| Completion Tokens | AI 生成的回复 Token 数 |
| Total Tokens | Prompt Tokens + Completion Tokens |

#### 5.3.2 各模块单次调用预算

| 模块 | 调用类型 | Prompt 上限 | Completion 上限 | Total 上限 |
|------|----------|------------|----------------|-----------|
| 03_训练 | RAG解法指导 | 1300 Token（含系统Prompt ~150 Token）| 400 Token | **1700 Token** |
| 04_助教 | 对话启发引导 | 1050 Token（含系统Prompt ~200 Token）| 800 Token | **1850 Token** |
| 02_五力 | 画像文字解读 | 800 Token | 500 Token | **1300 Token** |

#### 5.3.3 单次训练会话 Token 实际消耗估算

> **v2.0修正：** 原v1.1文档中"5000 Token/次训练会话"的联合预算与实际不符。
> 实际情况：5题训练，2题答错触发RAG，1次AI主动介入（3轮对话）：

```
实际消耗估算（5题训练典型场景）：

03_RAG：1700 Token/次 × 2次（2题答错）= 3400 Token
04_对话：1850 Token/次 × 3轮 = 5550 Token
────────────────────────────────────
典型会话总消耗：~8950 Token ≈ 9000 Token

控制策略：
  - 各模块独立控制自身 Token 上限（不做联合预算）
  - 每次 AI 调用记录至 ai_token_usage_log（student_id, module, tokens, provider, cost）
  - 当单次会话累计 > 15000 Token 时，后续 AI 调用降级至静态兜底
  - 该阈值从 system_configs 读取（key: session_max_token_budget）
```

#### 5.3.4 Token 裁剪优先级（04模块 Prompt 超过 1050 Token 时）

| 裁剪顺序 | 裁剪内容 | 节省量 |
|----------|----------|--------|
| 1（最先） | 历史对话从 10 轮减至 5 轮 | ~300 Token |
| 2 | 近期错题从 3 条减至 1 条 | ~100 Token |
| 3 | 五力画像从最弱2维度减至1维度 | ~40 Token |
| 4（最后保留） | 系统Prompt + 当前对话轮 | 不可裁剪 |

## 6. 跨模块数据流转协议

> **v2.0变更：** 数据字段类型已与 PostgreSQL DDL 对齐（UUID、BIGINT、TIMESTAMPTZ）。

### 6.1 五力画像读取优先级

所有模块读取学生五力画像时，统一调用 `five_power_service.get_current_ability(student_id)` 接口，该接口实现以下优先级逻辑：

```python
async def get_current_ability(student_id: int) -> dict:
    """
    综合查询：training × 0.6 + test × 0.4
    结果缓存至 Redis，TTL=5分钟（key: five_power:{student_id}）
    """
    train = await db.get(FivePowerTrainingProfile, student_id=student_id)
    test  = await db.get(FivePowerProfile, student_id=student_id, is_latest=True)

    if train and test:
        return blend(train, test, ratio=(0.6, 0.4))  # 综合得分
    elif test:
        return test.to_ability_dict()
    elif train:
        return train.to_ability_dict()
    else:
        raise NoPowerProfileError(student_id)   # ERR-001
```

**各模块对无画像情况的处理：**

| 模块 | NoPowerProfileError 时 |
|------|----------------------|
| 03_训练 | 返回 HTTP 403，前端跳转五力测试引导页 |
| 04_助教 | 进入通用模式（无五力定向），第一轮对话提示学生去测试 |

### 6.2 错题集跨模块状态机

```
wrong_answer_records.review_status 状态机：

[03模块] 学生答错 → INSERT wrong_answer_records (review_status='unreview')
      │
      ├── [04模块] 学生点击"AI复盘"
      │    → UPDATE review_status = 'reviewing', reviewed_at = NOW()
      │         │
      │         ├── AI 检测到理解突破（双重机制验证）
      │         │    → UPDATE review_status = 'aha_achieved', aha_at = NOW()  ← 终态
      │         │
      │         └── 复盘结束未突破
      │              → UPDATE review_status = 'pending_consolidation'
      │                       └── 再次复盘 → 回到 'reviewing'
      │
      └── [03模块] 同知识点重复答错≥2次
           → 通知 04 模块推送"推荐复盘"通知（不改变 review_status）
```

**状态枚举定义（PostgreSQL）：**

```sql
CREATE TYPE wrong_review_status AS ENUM (
```

## 7. 五力评分统一阈值规范

**本章定义全系统统一阈值，所有模块以此为准，不得各自重定义。**

### 7.1 五力得分分级标准

| 分级 | ability_score区间 | 等级标签 | 界面色 | 业务含义 |
|------|:----------------:|----------|--------|----------|
| 困难 | 0 ~ 49 | 重点强化项 | 🔴 红色 | 第一优先级训练，选题加权+40% |
| 需改进 | 50 ~ 64 | 次重点项 | 🟡 黄色 | 第二优先级训练，选题加权+20% |
| 良好 | 65 ~ 79 | 正常训练 | 🟢 绿色 | 按意愿训练，无额外加权 |
| 优秀 | 80 ~ 100 | 优势维度 | 💚 深绿 | 可用于借强补弱的入口力 |

> **重要**：分级基于 `ability_score`（能力分），**不使用** `final_score`（综合分）或 `preference_score`（入口分）。

### 7.2 各模块对阈值的使用规则

**02_五力认知测试模块（`focus_threshold` / `secondary_threshold`）：**
- `ability < 50`（`focus_threshold`）→ 重点强化项（🔴）
- `50 ≤ ability < 65`（`secondary_threshold`）→ 次重点项（🟡）
- `ability ≥ 65` → 正常/优秀

**03_个性化AI训练模块（选题权重）：**

```python
# algorithms/selection_weights.py
for force in FIVE_FORCES:
    base = 0.20  # 五力均分基础权重
    score = ability_scores[force]
    if score < 50:
        weights[force] = base + config.weak_boost_level1   # 默认0.40
    elif score < 65:
        weights[force] = base + config.weak_boost_level2   # 默认0.20
    else:
        weights[force] = base

weights = normalize(weights)  # 归一化，确保总和=1
```

**04_智能助教模块（AI对话倾向）：**
- `target_force`：ability_score 最低的力（始终存在）
- `preferred_force`：ability_score 最高的力（用于借强补弱）
- 关注维度：所有 `ability < 65` 的力（0~5个）
- 全部 `ability ≥ 65` 时：使用通用策略，不进行五力定向

### 7.3 学习模式路由规则

#### 7.3.1 两种学习模式定义

| 模式标识 | 中文名称 | 触发条件 | 五力的作用 |
|----------|----------|----------|-----------|
| `TRAIN_WEAKNESS` | 补足模式 | 任一力 ability < 65 | 决定**训练目标**（target_force）和选题权重 |
| `LEARN_BY_STRENGTH` | 一通百通模式 | 知识点首次学习 OR 所有力 ability ≥ 65 | 决定**教学入口**（preferred_force）|

#### 7.3.2 模式参数传递协议

`five_power_profiles` 表→03/04模块的参数链路（由 `five_power_service` 统一封装输出）：

```json
{
  "training_mode": "TRAIN_WEAKNESS",
  "target_force": "structure",
  "preferred_force": "insight"
}
```

| 参数 | 来源字段 | 类型 |
|------|----------|------|
| `training_mode` | `five_power_profiles.recommended_mode` | `VARCHAR(30)` |
| `target_force` | `five_power_profiles.primary_weakness` | `VARCHAR(20)` |
| `preferred_force` | `five_power_profiles.preferred_force` | `VARCHAR(20)` |

#### 7.3.3 借强补弱桥接策略

当 `training_mode = TRAIN_WEAKNESS` 且 `target_force ≠ preferred_force` 时，03/04模块均应应用以下桥接逻辑：

| target_force | preferred_force | 桥接动作 |
|-------------|----------------|---------|
| 建构力弱 | 洞察力强 | 先找变化量/不变量（洞察动作），再建立数量关系（建构动作）|
| 推演力弱 | 建构力强 | 先让学生把整体结构搭出来（A→B→C→D），再逐格推演 |
| 调适力弱 | 推演力强 | 让推演能力倒着检查全过程，成为错误检查工具 |
| 迁移力弱 | 洞察力强 | 先观察两题表面信息变化，用洞察剥离外壳看见同构 |
| 其他组合 | 任意优势力 | 从 preferred_force 对应思维动作切入，再过渡到 target_force |

**03模块应用**：题卷首题优先选 `secondary_power = preferred_force` 的题目（降低初始门槛）。
**04模块应用**：学生在 target_force 相关问题卡住时，AI 优先切换 preferred_force 引导话术。

## 8. 跨模块错误处理与降级链路

### 8.1 前置依赖失败的处理

| 模块 | 无五力画像（NoPowerProfileError）| AI不可用时 |
|------|--------------------------------|-----------|
| 03_训练 | 🔴 HTTP 403，跳转五力测试引导页 | 选题改平均权重（各20%），RAG降级展示静态解析 |
| 04_助教 | 🟡 允许进入通用模式，第一轮对话提示完成测试 | 展示静态知识卡片+FAQ |

### 8.2 RAG 降级完整时序

```
T=0s：   学生提交错误答案
T=0+200ms：写入 training_answer_records；异步推送至 Queue-C
            前端展示骨架屏：「🤖 AI 正在从你的薄弱维度分析解题思路…」（蓝色背景）
T=3s：   骨架屏加进度条动效
T=8s：   RAG 超时 → 触发降级：
            ├── questions.solution 存在 →
            │     展示静态解析（浅灰背景「⚡ 参考解析」，区别于AI实时回复）
            │     文案：「AI助手暂时繁忙，这是题目参考解析供参考」
            │     提供[重新生成]按钮（每题最多3次重试机会）
            └── questions.solution 不存在 →
                  展示「AI助手暂时繁忙，建议查看教材对应章节」
T=12s/15s：第1/2次重试等待时限（逐次延长）
T=15s：   第3次重试失败 → 移除重试按钮，仅显示降级内容
            记录降级事件至 system_downgrade_log，不计Token消耗
```

### 8.3 AI 服务全局降级策略

```
AI API 返回 5xx 或超时（>5s）时：

  03_训练（RAG）：
    → 展示 questions.solution 静态解析，标注「⚡ 参考解析」
    → 记录 training_answer_records.generation_status = 'degraded'

  04_助教（对话）：
    → 展示预置静态知识卡片（按当前知识点分类）
    → 展示「AI助教暂时休息，可以先查看这些参考内容」
    → 提供"知识点 FAQ"预置回答（后台可维护）

  共同处理：
    → INSERT system_downgrade_log (module, error_type, timestamp)
    → 不阻断主流程
    → 不记录Token消耗
```

### 8.4 统一错误码规范

| 错误码前缀 | 所属模块 | 示例 |
|-----------|---------|------|
| `AUTH-*` | 认证模块 | AUTH-001: Token过期；AUTH-002: 无权限 |

## 10. 异步任务队列协议

> **v2.0 新增章节。** 基于 Celery + Redis 的异步任务规范。

### 10.1 队列定义与职责

| 队列名 | 优先级 | 处理内容 | 超时 | 最大重试 |
|--------|--------|---------|------|---------|
| `queue_rag` | 高 | RAG解题思路生成（答错后触发）| 30s | 3次 |
| `queue_profile` | 中 | 训练五力画像EWMA更新（训练结束后）| 120s | 2次 |
| `queue_analysis` | 低 | AI个性化分析文字生成（测试完成后）| 60s | 2次 |
| `queue_annotation` | 低 | 题目AI自动标注（管理员上传题目后）| 300s | 1次 |

### 10.2 任务触发时机与数据传递

```
触发场景 → 任务名称 → 队列 → 输入参数

学生答错题目
  → rag_tasks.generate_hint
  → queue_rag
  → {answer_record_id: int, student_id: int, question_id: int, weak_forces: list}

训练会话结束
  → profile_tasks.update_training_profile
  → queue_profile
  → {student_id: int, session_id: UUID, answer_records: list}

五力测试完成
  → ai_analysis_tasks.generate_power_analysis
  → queue_analysis
  → {student_id: int, test_result_id: int, five_power_data: dict}

管理员上传题目
  → annotation_tasks.auto_annotate_question
  → queue_annotation
  → {question_id: int, stem: str, solution: str}
```

### 10.3 任务重试策略

```python
# 所有任务统一使用指数退避重试
@celery_app.task(
    bind=True,
    max_retries=3,
    default_retry_delay=60,      # 首次重试等60s
    retry_backoff=True,          # 指数退避：60s → 120s → 240s
    retry_jitter=True            # 加随机抖动，避免雪崩
)
def generate_hint(self, answer_record_id: int, ...):
    try:
        # 任务逻辑
        ...
    except LLMAPIError as exc:
        # LLM API错误：重试
        raise self.retry(exc=exc)
    except Exception as exc:
        # 其他错误：记录日志，不重试，降级处理
        logger.error(f"Task failed permanently: {exc}")
        mark_as_degraded(answer_record_id)
```

### 10.4 任务状态追踪

所有异步任务完成后需更新对应记录的状态字段，前端通过轮询查询：

| 任务 | 状态字段 | 状态枚举 |
|------|---------|---------|
| RAG生成 | `training_answer_records.generation_status` | `pending/completed/failed/degraded` |
| 训练画像更新 | `five_power_training_profiles.updated_at` | 更新时间戳即代表完成 |
| AI文字分析 | `five_power_profiles.ai_analysis_status` | `pending/processing/completed/failed` |
| 题目标注 | `question_annotations.annotation_status` | `pending/confirmed/failed` |

## 11. 安全标准

> **v2.0 新增章节。** 全系统横切安全规范，所有模块必须遵守。

### 11.1 密码与敏感数据加密

| 数据类型 | 加密方式 | 存储字段 | 用途 |
|---------|---------|---------|------|
| 管理员密码 | bcrypt（cost=12）| `admin_users.password_hash` | 登录校验 |
| 学生手机号（原文） | AES-128-CBC（Fernet）| `students.phone` | 解密后展示 |
| 学生手机号（查询） | SHA-256 + 盐值 | `students.phone_hash` | 唯一性校验，不可逆 |

**禁止事项：**
- ❌ 明文存储任何密码或手机号
- ❌ 将加密密钥硬编码在代码中（必须通过环境变量注入）
- ❌ 将 `.env` 文件提交至 Git（`.gitignore` 强制排除）

### 11.2 JWT 规范

```
算法：RS256（非对称签名，公私钥分离）
access_token：
  - 有效期：7天（学生）/ 8小时（管理员）
  - Payload：{"sub": student_id, "role": "student", "exp": timestamp}
refresh_token：
  - 有效期：30天
  - 刷新后旧Token立即加入 Redis 黑名单（TTL = 原Token剩余有效期）

多设备限制：
  同一学生同时最多1个 active chat_session
  第二台设备登录时，原设备 active 会话自动关闭（status → 'completed'）
  不强制踢出账号（只关闭会话，保持登录状态）
```

### 11.3 API 安全

| 防护类型 | 实现方式 | 阈值 |
|---------|---------|------|
| 接口限流 | Nginx limit_req（per IP）| 100 req/s（可配置）|
| 微信登录防重放 | Redis 缓存 code（TTL=5min，一次性消费）| — |
| 内容安全过滤 | LLM输出过滤（学生侧）| 触发 → 返回 ASST-002 |
| 管理员双因素 | 账号密码 + TOTP OTP | — |

### 11.4 未成年人数据保护

| 规则 | 实现 |
|------|------|
| 数据加密存储 | 手机号AES加密（见§11.1）|

## 13. 配置热更新机制

> **v2.0 新增章节。** 定义 `system_configs` 表的读写规范，确保参数修改无需重启服务。

### 13.1 system_configs 表规范

所有可调整的系统参数（算法阈值、Token预算、LLM供应商等）均存储于 `system_configs` 表：

```sql
CREATE TABLE system_configs (
    key         VARCHAR(100) PRIMARY KEY,
    value       TEXT NOT NULL,
    value_type  VARCHAR(20) DEFAULT 'string', -- string/number/json/boolean
    description TEXT,
    updated_at  TIMESTAMPTZ DEFAULT NOW()
);
```

### 13.2 参数读取规则

**所有模块统一通过 `config_service.get(key)` 读取参数，禁止直接查询 DB。**

```python
# 读取顺序（缓存优先）：
# 1. Redis 缓存（key: config:{key}，TTL=5分钟）
# 2. Redis 未命中 → 查询 PostgreSQL → 写入 Redis 缓存
# 3. PostgreSQL 查询失败 → 使用代码内 fallback 默认值（绝不中断服务）

async def get(key: str, default=None):
    cached = await redis.get(f"config:{key}")
    if cached:
        return parse(cached)
    db_value = await db.get_config(key)
    if db_value:
        await redis.setex(f"config:{key}", 300, db_value.value)
        return parse(db_value.value)
    return default
```

### 13.3 参数修改规则

管理员通过后台修改参数时，系统自动：
1. 更新 `system_configs` 表
2. 删除 Redis 对应缓存（`DEL config:{key}`）
3. 下次服务调用时自动读取新值，**无需重启**
