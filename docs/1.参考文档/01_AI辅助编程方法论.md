## 1. 核心理念：人机分工定位

> **你是指挥，AI 是乐团——你想清楚做什么，它执行细节。**

Vibe Coding 的本质不是"让 AI 写代码"，而是建立一套**结构化的人机协作流程**，让 AI 在明确边界内高效执行，人负责判断与决策。

### 1.1 AI 擅长的事

| 类型 | 具体内容 |
|------|----------|
| 重复性模式生成 | CRUD、Get/Set、Builder 模式 |
| 样板代码 | Spring Boot 初始化、配置类 |
| 文档生成 | README、接口文档、注释 |
| 多方案对比 | 给出 3 种实现，各有优劣 |

### 1.2 人必须负责的事

| 类型 | 原因 |
|------|------|
| 需求判断（这个功能该不该做） | AI 不了解业务背景与优先级 |
| 架构决策（这个模块怎么拆分） | 涉及全局一致性，AI 只见局部 |
| 代码审核（这段逻辑对不对） | AI 会自信地写出错误逻辑 |
| 特殊情况处理（边界条件、异常流程） | 业务边界必须由人定义 |
| 架构决策、业务判断 | AI 会自信地做出错误决策 |

**关键认知：** 模糊的指令 → AI 靠猜 → 猜错了浪费轮次 → 你来返工。结构化流程让 AI 理解清晰的边界，大幅减少无效对话。

## 2. 五个核心命令

这五个命令解决的是与 AI 长期协作中最常见的**交互问题**。

### 2.1 `/btw` — 临时提问，不打扰主任务

**场景：** 你正在开发一个功能，突然想起一个技术问题想问 AI，但又不想这个问题进入上下文，影响当前任务。

```
/btw Spring Boot 中 @ConfigurationProperties 和 @Value 的区别是什么？
```

**效果：** AI 回答后，这个对话不会污染你的主任务上下文。

> **拓展：** `/btw` 本质上是一次"沙盒提问"。适用于快速查询 API 用法、语法确认、工具比较等不需要纳入任务上下文的场景。

---

### 2.2 `/compact` + `/context` — 主动管理上下文容量

**场景：** 你要开始一个重要任务（如重构、架构设计），担心 AI 在执行过程中自动压缩上下文导致关键信息丢失。

```
/context   # 先看当前上下文占用
/compact   # 主动压缩摘要
```

**使用建议：**
- 重要任务执行前，先用 `/context` 检查上下文容量
- 容量不足时先 `/compact`，再开始任务
- 不要等 AI 自动压缩——自动压缩可能丢失你认为重要的细节

---

### 2.3 `/rename` — 给会话起个好认的名字

**场景：** 你同时在做多个任务，想让会话管理更清晰。

```
/rename 用户模块重构
```

**建议：** 用当前正在开发的任务名命名，方便后续 `/resume` 时快速定位。

---

### 2.4 `/resume` — 在多个任务之间切换

**场景：** 你在 A 项目做了很多准备工作，现在切换到 B 项目，B 项目的上下文是全新的。

```
/resume   # 切换到指定会话
```

**配合 `/rename` 使用效果最佳：** 命名清晰的会话，切换时一目了然。

---

### 2.5 `/rewind` — 回退到之前的某个节点

**场景：** AI 跑偏了，代码改错了，或者上下文已经被污染，想回到更早的节点重新来过。

```
/rewind
```

**适用情形：**
- AI 产出了完全不符合需求的代码
- 上下文被错误信息污染
- 想尝试另一条实现路径

> **拓展：** `/rewind` 是 Vibe Coding 的"后悔药"。在复杂任务中，建议在关键节点前用 `/rename` 打标记，出问题后可以精准回退，而不是从头开始。

## 3. 标准 Prompt 模板

### 3.1 推荐格式（md 格式）

```markdown
## 系统角色
你是一名资深的 Java 开发工程师，拥有大量领域的开发经验，代码规范、注释完整、兼容性强

## 需求背景
我需要做一个 XX 功能（项目），用于 XX 场景，解决 XX 问题

## 核心目标
1. 目标 1
2. 目标 2

## 输出规范
1. 使用 JSON 格式输出
2. 代码必须有完整的中文注释

## 约束条件
1. 必须使用 JDK 11+，Spring Boot 版本大于 3.5
2. 每个类必须不超过 200 行代码

## 验收标准
用户输入 XXX，预期输出结果 XXX
```

### 3.2 六要素详解

| 要素 | 作用 | 常见错误 |
|------|------|----------|
| **系统角色** | 让 AI 进入正确的专业上下文 | 不写或写得太泛 |
| **需求背景** | 让 AI 理解做这件事的原因和动机 | 跳过，直接给功能 |
| **核心目标** | 明确交付物是什么 | 目标太多，没有优先级 |
| **输出规范** | 指定输出格式、注释风格等 | 让 AI 自由发挥 |
| **约束条件** | 技术限制、代码规范、边界条件 | **最重要但最容易被忽略** |
| **验收标准** | 描述"输入什么→输出什么" | 写得太模糊无法自测 |

### 3.3 为什么每个要素都重要

- **系统角色** — 让 AI 进入正确的专业上下文，否则 AI 给你一个初学者级别的方案
- **需求背景** — 说明做这件事的原因，AI 会据此判断优先级
- **核心目标** — 明确要交付什么，避免做了一堆无关的东西
- **约束条件** — 这是最容易忽略、也是最有价值的部分，技术限制必须说清楚
- **验收标准** — 描述清楚"输入什么→输出什么"，AI 可以自测

## 4. 全新项目开发：从想法到可运行代码

全新项目开发遵循一个**七步工作流**，每一步都有明确的产出物。

### 第一步：聊想法

把你的想法完整说出来。AI 不是读心者，你想得越清楚，AI 理解得越准确。

**推荐话术模板：**

```
我想做一个 [产品名称]
主要是为了解决 [什么问题]
目标用户是 [who]
核心功能包括：
  1. [功能1]
  2. [功能2]
核心功能验收标准：
  1. [功能1的验收标准为 XXX]
  2. [功能2的验收标准为 XXX]
我希望它能 [达到什么效果]
```

---

### 第二步：要 PRD

直接输入：

```
帮我将刚才的内容整理成一份产品需求文档（PRD.md）
```

AI 会生成一份包含以下内容的 PRD：
- 产品定位
- 核心功能列表
- 验收标准
- 用户流程
- 技术要求（初稿）

**拿到 PRD 后：** 逐条阅读，对照自己最初的想法，看 AI 理解得是否一致。发现偏差当场修改，不要等到代码写完了才发现。

---

### 第三步：明确项目目标

PRD 解决了"做什么"，接下来要定"做到什么程度"——这直接影响技术方案选型。

**直接告诉 AI 你的真实目标：**

```
项目目标是 [商业级 | 自用 | 学习]
并发要求：[高并发 | 低并发 | 单机即可]
质量要求：[生产级 | 能跑就行]
```

**示例（正式系统）：**

```
需要稳定的数据库，比如 PostgreSQL
不需要编写用户登录注册，用现有的 SSO 单点登录集成
所有涉及密码的地方需要做加密处理
需要支持分布式和高并发
需要考虑性能优化和未来扩展性
```

---

### 第四步：确定技术栈

让 AI 推荐并解释原因：

```
我想做一个 [项目描述]
项目目标是 [商业|自用]
我的技术水平为 [零基础/有基础]
请推荐合适的技术栈，并说明为什么这么选择
选择技术栈核心原则为：
  1. 选取主流：遇到问题容易找到解决方案，公开资料多
  2. 选成熟的：工具链完善，坑少
  3. 选适合的：匹配项目规模，不要过度设计
```

---

### 第五步：架构设计

有了 PRD 和技术栈，让 AI 设计整体架构：

```
根据当前的 PRD.md 文档，请为我设计当前项目的架构，包括：
  1. 项目目录结构
  2. 核心模块划分
  3. 数据模型设计
  4. 代码规范建议
我的技术背景为：[你的水平]
我希望这个项目：[可部署|同时支持拓展]
```

---

### 第六步：整理项目文档

让 AI 在项目根目录下自动生成两份核心文档：

**README.md：**
```markdown
# 项目名称
- 项目简介：该项目是干什么的
- 如何运行：如何运行该项目
- 技术栈：选用了哪些技术
```

**ARCHITECTURE.md：**
```markdown
# 架构文档
- 技术栈选择及原因
- 项目目录结构
- 核心模块说明
- 数据模型设计
- 代码规范
```

---

### 第七步：编译验证

代码写完后，不要等 CI 来告诉你报错——让 AI 立刻执行编译：

```
请执行 Maven 编译，检查是否有编译错误
```

如果报错了，AI 直接修复，循环直到编译通过。

> **全新项目七步工作流：**
> ```
> 聊想法 → PRD → 明确目标 → 确定技术栈 → 架构设计 → 整理文档 → 编译验证
> ```

## 5. 历史项目接入：扫描、索引与规格驱动

### 核心思路：让 AI 先读懂项目，再动手

处理历史项目，第一步不是写代码，而是让 AI 理解项目结构。这需要两步：**生成索引文档 + 建立规格约束**。

---

### 第一步：扫描源码，生成模块大纲

**方式一：手动 Prompt**

```
我想按照以下方式完成已有大型项目的拓展开发：
让 LLM 大模型先扫源码，生成服务结构和模块大纲等文件，
以便大模型基于这些索引和具体内容来理解代码。
同时代码改完后，大纲也要同步更新，维持最新的大纲文件，
同时通过 CLAUDE.md 来声明文档路径和使用规则，
以便以后续的 LLM 会话自动利用这些大纲文档。
```

**方式二：使用 skill（推荐，一句话搞定）**

```
/project-outline
```

执行后，AI 会：
1. 扫描项目源码
2. 生成 `INDEX.md`（项目总索引）
3. 生成各模块独立的大纲文件
4. 自动更新 `CLAUDE.md`，声明文档路径和使用规则

**关键原则：代码修改完后，必须同步更新大纲文件。**

---

### 第二步：规格驱动开发（Plan + Spec）

当有新需求要开发时，使用 `/brainstorming` 启动设计流程：

```
/brainstorming
```

**Plan 理念：** 聚焦"怎么做"——Agent 收到需求后，分析出执行步骤计划

**Spec 理念：** 聚焦"对什么负责"——所有执行工作必须严格对齐规格文档

**两者结合：先设计，再执行；设计文档是一切的标准。**

实际使用中，只需调用 `/brainstorming` + 描述你的开发需求，AI 会自动完成 Plan + Spec 步骤。

---

### 第三步：CLAUDE.md 约束声明

在项目根目录的 `CLAUDE.md` 中声明文档路径和使用规则：

```markdown
# 项目规范

## 文档索引
- 源码大纲：`docs/index.md`
- 模块大纲：`docs/modules/`

## 开发规则
- Maven 路径：`D:\tools\Maven`
- 每个类不超过 200 行代码
- 所有 API 接口必须有中文注释

## 使用方法
新会话开始时，AI 会自动读取以上文档，无需重复介绍项目背景。
```

---

### 第四步：编译验证

同全新项目，代码完成后立即执行编译：

```
请执行 Maven 编译，检查是否有编译错误
```

> **历史项目四步工作流：**
> ```
> 扫描源码生成大纲 → 规格驱动开发 → CLAUDE.md 约束声明 → 编译验证
> ```

## 6. Prompt 工程与高效人机协作

### 6.1 结构化 Prompt 的必要性

很多人写 prompt 是这样的："帮我写一个用户模块"——然后得到一段不知道往哪放的散装代码。

**问题不在 AI，在于 Prompt 太模糊：**

```
模糊的指令 → AI 靠猜 → 猜错了浪费轮次 → 你来返工
```

结构化模板让 AI 理解清晰的边界，大幅减少无效对话。

---

### 6.2 约束条件：最有价值的部分

为什么约束条件最容易被忽略？因为写约束条件需要你想清楚技术上**什么不能做**。

**常见的约束条件：**

- JDK 版本、框架版本
- 每个类不超过 N 行代码
- 不使用某项技术（如禁止 `for` 循环，改用 Stream API）
- 所有密码必须加密存储
- API 响应时间不超过 X ms
- 不引入新的第三方依赖
- 数据库操作必须使用事务

**约束条件的价值：** 明确告知技术限制后，AI 不会产出"技术上无法落地"的方案。

---

### 6.3 验收标准即测试用例

好的验收标准示例：

```
用户输入：手机号 13800138000，密码 123456
预期输出：注册成功，返回用户 ID = 1，HTTP 200

用户输入：已注册手机号 13800138000，密码 123456
预期输出：注册失败，返回错误码 USER_EXISTS，HTTP 409
```

AI 看到这个标准，可以自我验证：我写的逻辑是否满足这两种情况？

**验收标准的写法原则：**
1. 输入具体，不用"某个用户"——用真实数据举例
2. 输出明确，包含返回码、返回格式、关键字段
3. 覆盖正常路径和异常路径
4. AI 能据此自测，无需人工逐行检查

---

### 6.4 人机协作最佳分工

```
┌─────────────────────────────────────────┐
│              人负责                      │
│  • 需求判断（该不该做）                   │
│  • 架构决策（怎么拆）                     │
│  • 代码审核（逻辑对不对）                 │
│  • 边界条件与异常流程                     │
└───────────────────┬─────────────────────┘
                    │ 明确指令
                    ▼
┌─────────────────────────────────────────┐
│              AI 执行                     │
│  • 重复性模式生成（CRUD、Builder 模式）   │
│  • 样板代码（初始化、配置类）             │
│  • 文档生成（README、接口文档、注释）     │
│  • 多方案对比（3种实现各有优劣）          │
└─────────────────────────────────────────┘
```

## 7. 团队规范落地与最佳实践

### 7.1 CLAUDE.md 的团队价值

`CLAUDE.md` 是项目级规范文档，放在项目根目录。它的核心价值是：**减少每次的重复交代。**

| 场景 | 没有 CLAUDE.md | 有 CLAUDE.md |
|------|----------------|--------------|
| 新成员加入 | 需要手动介绍项目背景、技术栈、编码规范——每次 AI 会话都要说一遍 | 新成员 clone 项目后，AI 自动读取项目文档，快速理解上下文 |
| 日常开发 | 每次新会话重复说明约束条件 | AI 自动遵守已声明的规范 |
| 代码审核 | 手动对照规范逐条检查 | 直接让 AI 检查是否符合 CLAUDE.md 声明的约束 |

**CLAUDE.md 应该包含的内容：**

- 项目简介和技术栈说明
- 源码大纲和模块结构的路径
- 开发规范（命名、类长度限制、Maven 路径等）
- 验收标准示例
- 常用命令和脚本

---

### 7.2 大纲文件的维护机制

代码变更后同步更新 `INDEX.md`，这是需要纳入开发流程的约定：

```
开发流程约定：
1. 每次功能开发完成后
2. 同步更新 docs/index.md 和对应模块大纲
3. 确保后续 AI 会话看到的索引是最新的
```

**关键原则：代码改了，大纲必须同步更新。** 否则后续 AI 会话基于过时的大纲作出错误判断。

---

### 7.3 Maven 路径统一配置

在 `CLAUDE.md` 中声明当前项目使用的 Maven 路径，避免编译环境不一致：

```markdown
## 环境配置

### Maven
- Maven 路径：`D:\tools\Maven`
- 使用方式：`D:\tools\Maven\bin\mvn.cmd`（不依赖系统 PATH）
```

---

### 7.4 团队协作场景

**场景一：新成员加入**

1. 新成员 clone 项目
2. AI 读取 `CLAUDE.md` + `INDEX.md`，自动理解项目结构
3. 无需手动介绍，直接上手开发

**场景二：AI 产出代码的审核要点**

- 是否符合 `CLAUDE.md` 中声明的约束条件（版本、代码行数限制等）
- 架构是否与项目整体结构一致
- 验收标准是否满足

## 8. 避坑提示

### 坑一：没有规格文档就让 AI 写大量代码

**现象：** AI 会自由发挥，产出难以审核和回滚的代码。

**正确做法：**
1. 先用 `/brainstorming` 出规格文档
2. 人工审批规格文档
3. 审批通过后再开始写代码

> **底层原因：** 没有规格文档，AI 不知道边界在哪里，只能根据最表面的理解生成代码。后期改动成本极高。

---

### 坑二：忽略上下文压缩导致关键信息丢失

**现象：** AI 在执行复杂任务时，悄悄压缩了上下文，把之前确认的关键约束丢掉了。

**正确做法：**
- 重要任务执行前，用 `/context` 检查上下文容量
- 必要时先 `/compact`，再开始任务
- 不要等 AI 自动压缩

---

### 坑三：把所有判断都交给 AI

**现象：** AI 会自信地做出错误决策，且表现得很确定。

**正确做法：** 架构决策、业务判断、异常情况处理，这些**必须由人负责**。

> **底层原因：** AI 没有业务上下文，也没有历史经验，面对不确定性时它会选择一个"看起来合理"的答案，而不是承认不确定。

## 9. 核心方法论总结与行动建议

### 9.1 核心方法论回顾

| 维度 | 核心要点 |
|------|----------|
| **定位** | 你是指挥，AI 是乐团——你想清楚做什么，它执行细节 |
| **命令** | 5 个核心命令解决交互问题：`/btw`、`/compact`、`/rename`、`/resume`、`/rewind` |

2. **用 `/project-outline` 生成源码大纲**

## 10. 拓展：方法论深度解读

### 10.1 为什么这套方法论有效

Vibe Coding 的本质是把软件工程的核心实践（需求分析、架构设计、规格驱动开发、代码审查）与 AI 的执行能力结合起来。

传统开发中，这些实践往往因为"时间紧"被跳过。AI 的出现反而倒逼开发者回归正确的工程实践——因为不写清楚需求，AI 就会乱写，你必须想清楚才能给出好的 Prompt。

**结构化 Prompt = 结构化思维的外化。** 写好 Prompt 的过程，本身就是在做设计。

---

### 10.2 CLAUDE.md 与大纲文件体系的深层价值

```
CLAUDE.md                  → 项目约束与规范（静态，变化慢）
docs/index.md              → 项目总索引（随代码变化）
docs/modules/xxx.md        → 各模块大纲（随模块变化）
```

这三个文件共同构成了 **AI 的"项目记忆"**。每次新会话，AI 自动读取这三类文件，相当于把一个有经验的老员工的背景知识注入给 AI。

**核心价值：消除 AI 会话的无状态性。**

---

### 10.3 规格驱动开发（Spec-Driven Development）的工程含义

`/brainstorming` 触发的 Plan + Spec 流程，对应软件工程中的：

| AI 流程 | 对应工程实践 |
|---------|------------|
| Plan（执行步骤计划） | 任务分解（WBS）、开发计划 |
| Spec（规格文档） | 功能规格说明书（FRS）、接口契约 |

**核心原则：先设计，再执行；设计文档是一切的标准。**

这与 TDD（测试驱动开发）的理念一致：先定义"什么叫做对"，再写代码去满足这个定义。

---

### 10.4 上下文管理的重要性

AI 的上下文窗口是有限的，当对话轮次增多，AI 会自动压缩早期内容。这个压缩过程是不透明的，可能导致：

- 之前确认的技术约束被遗忘
- AI 重新"发明"已经否定过的方案
- 代码风格前后不一致

**主动上下文管理策略：**

```
长任务 → 定期检查 /context → 容量不足时 /compact → 继续任务
关键节点 → /rename 打标记 → 出问题时 /rewind 回退
临时问题 → /btw 隔离提问 → 不污染主上下文
```

---

### 10.5 验收标准的工程价值

验收标准不仅是给 AI 看的，更是给自己看的：

1. **澄清需求**：写验收标准时，你会发现之前"想当然"的地方
2. **测试用例**：好的验收标准直接就是单元测试的输入输出
3. **验收基准**：上线前对照验收标准逐条验证，避免遗漏

**验收标准模板：**

```
正常情况：
  输入：[具体输入]
  预期输出：[具体输出，含状态码/格式]

边界情况：
  输入：[边界值]
  预期输出：[边界情况的期望行为]

异常情况：
  输入：[错误输入]
  预期输出：[错误码、错误信息、HTTP 状态]
```

---

### 10.6 团队推广路径建议

**第一阶段：个人实践（1~2周）**
- 在自己的项目中实践 Vibe Coding 完整流程
- 建立对 5 个核心命令的肌肉记忆
- 积累自己的 Prompt 模板库

**第二阶段：小组推广（1个月）**
- 选 1~2 个新项目试点
- 统一 CLAUDE.md 模板
- 建立大纲文件维护约定

**第三阶段：团队规范化（持续迭代）**
- 将 CLAUDE.md 维护纳入 PR 检查流程
- 积累团队级 Prompt 模板库
- 定期复盘 AI 产出质量，优化约束条件
