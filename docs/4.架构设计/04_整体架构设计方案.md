## 1. 技术选型决策

### 1.1 选型总览

| 层级 | 技术 | 版本 | 选型理由 |
|------|------|------|----------|
| **小程序端** | WXML + TypeScript + Vant Weapp | miniprogram-api-typings 3.x | 微信原生框架，覆盖率最高；Vant Weapp 组件库完善，坑少 |
| **小程序端·状态** | MobX-miniprogram | 1.x | 官方推荐状态管理方案，适配小程序生命周期 |
| **小程序端·图表** | wx-charts | 2.x | 轻量级图表库，支持五边形雷达图渲染 |
| **小程序端·公式** | WxKaTeX | 0.16+ | LaTeX 数学公式渲染，数理化题目必需 |
| **管理后台前端** | Vue 3 + TypeScript + Vite + Element Plus | Vue 3.4+ | 生态成熟，文档丰富，与业务逻辑解耦 |
| **后端框架** | Python · FastAPI | 0.110+ | 异步原生、自动生成 OpenAPI 文档、Pydantic 类型校验、AI/ML 生态最佳 |
| **ASGI 服务器** | Gunicorn + Uvicorn workers | Gunicorn 21+ | 开发环境用 uvicorn 单进程；生产环境用 gunicorn 管理多个 uvicorn worker 进程 |
| **关系型数据库** | PostgreSQL | 16+ | 稳定可靠，JSONB 支持灵活结构，全文检索，丰富的索引类型 |
| **DB 驱动** | asyncpg | 0.29+ | PostgreSQL 异步驱动，与 SQLAlchemy async 配合，性能最优 |
| **缓存/消息** | Redis | 7.x | JWT 黑名单、会话缓存、Celery Broker、热数据缓存 |
| **异步任务队列** | Celery + Redis | Celery 5.x | RAG 生成、画像更新等异步任务；Python 生态原生支持 |
| **向量数据库** | ChromaDB | 0.5+ | Python 原生、部署简单、无需 Java 运行时；V2.0 可平滑迁移 Milvus |
| **Embedding API** | DashScope（通义 text-embedding-v2）| API | 文本向量化，用于题目和策略文档入库 ChromaDB；维度 1536；与 LLM 供应商统一账户，降低接入复杂度 |
| **ORM** | SQLAlchemy (async) | 2.x | 成熟稳定，支持 asyncio，类型提示完善 |
| **数据库迁移** | Alembic | 1.13+ | 与 SQLAlchemy 深度集成，版本管理清晰 |
| **对象存储** | 阿里云 OSS / MinIO | — | 图片（题目图片、用户头像）、PDF 报告存储；MinIO 可本地自托管 |
| **API 网关** | Nginx | 1.25+ | 反向代理、SSL 终止、限流、静态文件服务 |
| **SSL 证书** | Let's Encrypt + Certbot | — | 免费自动续签；域名验证后自动颁发，certbot cron 定期续签 |
| **容器化** | Docker + Docker Compose | Docker 24+ | 环境一致性，V2.0 可平滑迁移 K8s |
| **日志库** | Loguru | 0.7+ | 结构化 JSON 日志，比标准 logging 更简洁；生产环境输出 JSON 供日志采集 |
| **密码加密** | passlib (bcrypt) | 1.7+ | 管理员密码 bcrypt 哈希，cost=12 |
| **数据加密** | cryptography (Fernet) | 41+ | 手机号 AES-128-CBC 加密存储 |
| **JWT** | python-jose | 3.3+ | RS256 非对称签名，公私钥分离 |
| **配置管理** | pydantic-settings | 2.x | 从环境变量读取强类型配置，与 FastAPI 无缝集成 |

### 1.2 后端框架选型详解：为什么选 FastAPI

```
对比维度        FastAPI (Python)    Django (Python)    Spring Boot (Java)
────────────────────────────────────────────────────────────────────────
AI/ML 生态       ★★★★★              ★★★                ★★
异步支持         原生 async/await    需要额外配置         Reactor/WebFlux
类型安全         Pydantic 强类型     弱                  强
上手难度         低                  中                  高
自动文档         原生 OpenAPI        django-rest          Swagger 手动
团队规模         小团队友好          中大团队             企业级
适合本项目       ✅ 最优             适合但过重            过度设计
```

**结论**：项目核心壁垒是五力算法和 AI 调用，Python 在此生态最强；FastAPI 轻量、高性能、文档好，适合本项目规模。

### 1.3 前端选型说明（小程序端）

```
小程序端完整依赖（package.json 核心依赖）：
  原生框架：WXML + TypeScript（官方支持最好，最稳定）
  UI 组件：@vant/weapp ^1.10.x（开源，组件丰富，文档完善，坑少）
  状态管理：mobx-miniprogram ^4.x + mobx-miniprogram-bindings ^2.x
  数学公式：wxkatex ^0.16.x（LaTeX 公式渲染，数理化题目必须）
  HTTP 请求：自行封装（基于 wx.request，统一拦截器、Token 刷新、错误处理）
  图表：wx-charts ^2.x（五边形雷达图渲染，轻量，不依赖 canvas 2D API）
  类型声明：miniprogram-api-typings ^3.x（微信 API TypeScript 类型）

注意：wx-charts 与 echarts-for-weixin 均可实现雷达图；wx-charts 包体更小（<20KB），
      优先选用；若后续需要更复杂的图表可按需替换为 echarts-for-weixin。
```

### 2.2 请求链路示意

```
[学生答错题目] 完整链路：

微信小程序
  │ POST /api/v1/training/answer
  ▼
Nginx → FastAPI
  │ 1. 同步判题 (is_correct = false)，≤1s
  │ 2. 写入 training_answer_records
  │ 3. 写入 wrong_answer_records (review_status=unreview)
  │ 4. 触发异步任务 [task: generate_rag_hint(question_id, student_id)]
  ▼
Redis (Celery Broker)
  │ 推送任务到 RAG worker 队列
  ▼
Celery Worker (RAG 任务)
  │ 1. 从 ChromaDB 双路召回（相似题解析 + 五力策略文档）
  │ 2. 组装 Prompt（≤1300 Token）
  │ 3. 调用 LLM API → 生成解题思路（≤400字）
  │ 4. 写入 training_answer_records.rag_content
  │ 5. 更新 generation_status = completed
  ▼
小程序端轮询 GET /api/v1/training/rag-status/{answer_id}
  │ 拿到结果后展示（蓝色气泡 "🤖 AI解题思路"）
  │ 超时(>8s)：展示静态降级（浅灰色 "⚡ 参考解析"）
```

```
            │ 调用                   │
            └─────────────────────► algorithms/
```

### 4.2 六大核心服务详解

#### Module 1：认证服务（auth_service）
```python
功能：
  - 微信 code2session → 获取 openid
  - JWT 签发（access_token 7天 + refresh_token 30天）
  - 手机号绑定（微信加密数据解密）
  - Token 刷新（Redis 黑名单机制）
  - 管理员双因素认证（账号+OTP）

关键逻辑：
  - 密码使用 bcrypt 哈希（管理员账户）
  - JWT 使用 RS256 非对称签名
  - Redis 存储已登出 Token（黑名单，7天 TTL）
  - 同一学生同时最多1个 active 会话（多设备限制）
```

#### Module 2：五力评分服务（test_service + algorithms/）
```python
功能：
  - 组卷（从 cognitive_questions 取20道固定题目，按打散顺序输出）
  - 测试中断恢复（Redis 缓存进度，保留72h）
  - 同步评分（测试完成后≤3s）：
      → ability_score：标准答案题评分（A1~A4）
      → preference_score：无唯一答案题权重累积（B1~B3）
      → final_score：70% ability + 30% preference（Module C）
      → 画像分析：薄弱项/优势入口/错位分析/模式推荐（Module D）
  - 异步 AI 文字解读（Celery 任务，≤30s）

关键约束：
  - 评分算法纯函数化，独立于IO，100% 可单元测试
  - 所有评分参数从 system_configs 读取，支持热更新
```

#### Module 3：个性化训练服务（training_service）
```python
功能：
  - 读取当前五力画像（training × 0.6 + test × 0.4 融合）
  - 运行选题算法（Module F）：
      TRAIN_WEAKNESS 模式：双档加权（<50分+40%，50~65分+20%）
      LEARN_BY_STRENGTH 模式：preferred_force 占 50%
  - 桥接策略：首题优先选 secondary_power=preferred_force 的题
  - 触发 RAG 任务（答错后，异步入队）
  - 连续答错≥2 → 通知 assistant_service 主动介入判断
  - 训练结束后：Celery 任务异步更新 five_power_training_profiles（EWMA）

关键接口：
  POST /api/v1/training/mini-session   # 04模块调度的微训练（2~3题）
  GET  /api/v1/training/rag-status/{id} # 前端轮询RAG生成状态（3s间隔）
```

#### Module 4：RAG 服务（rag_service）
```python
功能：
  1. 路径1：向 ChromaDB 检索相似题解析（top_k=3，过滤薄弱五力）
  2. 路径2：向 ChromaDB 检索五力策略文档（top_k=2，按薄弱力匹配）
  3. 结果合并 → 组装五力专项 Prompt（≤1300 Token）
  4. 调用 LLM → 生成解题思路（≤400字）
  5. 写入 training_answer_records.rag_content

降级链路：
  T=8s 超时 → 查 questions.solution 字段展示静态解析
  solution 不存在 → 展示"建议查看教材" + 重试按钮（3次机会）

向量化流程（题目入库时触发）：
  题目发布 → Celery 任务 → Embedding（句向量）→ 写入 ChromaDB
  集合：collection_questions（题目解析库）
         collection_strategies（五力策略文档库，预置20~30篇）
```

#### Module 5：智能助教服务（assistant_service）
```python
功能：
  - 组装学习状态快照（≤500ms）：
      五力画像摘要 + 近期错题(3条) + 历史对话(10轮) + 策略指令
  - AI 介入时机决策（5个前置条件全部满足才触发）
  - 启发策略查询：查 ai_student_strategy_profiles → 按 ES 降序选策略
  - 策略切换：同一策略2次无效 → 自动切换
  - 理解突破检测：AI语义判断 + 规则兜底（训练答题正确率≥80%）
  - 沉默模式管理（触发/解除/10分钟超时）
  - Token 裁剪（超限时：历史对话→错题摘要→五力画像，逐步裁减）

关键限制：
  每会话最多 30 轮对话
  AI 主动介入 ≤3次/会话
  沉默模式超时 10 分钟自动解除
```

#### Module 6：LLM 适配器（llm_adapter）
```python
# 统一接口，屏蔽多供应商差异
class LLMAdapter:
    async def chat(
        self,
        messages: list[Message],
        max_tokens: int,
        temperature: float = 0.7,
        stream: bool = False
    ) -> LLMResponse:
        provider = self._get_active_provider()  # 从 Redis 缓存读取当前供应商
        if provider == "tongyi":
            return await self._call_tongyi(messages, max_tokens, temperature)
        elif provider == "openai":
            return await self._call_openai(messages, max_tokens, temperature)
        # ... 其他供应商

支持供应商（配置化切换，无需重启）：
  - 通义千问（推荐 V1.0，成本低，国内合规）
  - DeepSeek（备选，性价比高）
  - OpenAI（高精度备选，成本较高）
```

### 6.3 题库存储策略与向量数据库介入时机

#### 6.3.1 题库有两类性质不同的数据

项目中存在两类题目，存储策略完全不同：

| 类型 | 数量 | 查询方式 | 存储 |
|------|------|----------|------|
| **五力认知测试题** | 固定 20 道 | 按 `question_no` 精确查找 | PostgreSQL 即可 |
| **训练题库** | V1.0 约 1280 道 | 按知识点+五力+难度精确过滤 | PostgreSQL 主存储 + ChromaDB 语义索引 |

#### 6.3.2 PostgreSQL 是题库的唯一主存储

训练题库的**选题算法**是结构化精确过滤，不是语义相似度检索，PostgreSQL 完全胜任：

```sql
-- 选题算法的实际 SQL（Module F）——完全不需要向量数据库
SELECT id FROM questions
WHERE knowledge_point_id = 1234          -- 精确匹配知识点
  AND primary_power = 'STRUCTURE'         -- 精确匹配训练五力
  AND difficulty = 'basic'               -- 精确匹配难度
  AND status = 'published'
  AND deleted_at IS NULL
  AND id NOT IN (SELECT question_id FROM training_answer_records
                 WHERE session_id IN (...))  -- 去重窗口
ORDER BY RANDOM()
LIMIT 2;
```

**V1.0 规模不需要担忧：**
```
1280 道题 × 平均 2KB/题 ≈ 2.5MB —— PostgreSQL 毫无压力
即便扩展到 10 万道题，PostgreSQL 依然从容应对
```

#### 6.3.3 两个数据库的职责边界

```
┌─────────────────────────────────────────────────────────────────┐
│                         题库存储分层                              │
│                                                                 │
│   PostgreSQL（主存储）                ChromaDB（语义检索索引）    │
│   ──────────────────                 ────────────────────────   │
│   ✅ 题目完整内容（Source of Truth）  ✅ 题目+解析的语义向量       │
│   ✅ 结构化字段精确过滤选题            ✅ 相似题语义召回（RAG路径1）│
│   ✅ 难度/五力/知识点标签过滤          ✅ 五力策略文档检索（RAG路径2）│
│   ✅ 参考解析（RAG降级时展示）         ❌ 不存原始完整文本         │
│   ✅ 管理员增删改查                   ❌ 不做精确条件过滤          │
│                                                                 │
│   ChromaDB 是 PostgreSQL 的"派生索引"                           │
│   可随时从 PostgreSQL 数据重建，不是独立数据源                    │
└─────────────────────────────────────────────────────────────────┘
```

**关键认知：ChromaDB 只服务于一个场景** —— 学生答错后，RAG 生成解题思路时的语义检索。选题不需要它。

#### 6.3.4 向量数据库的分阶段介入

```
Sprint 1~2（开发调试阶段）
─────────────────────────────────────────────────────────────

  RAG：直接展示 questions.solution 静态内容，或 mock 固定文本

  目标：答错后能收到有意义的 AI 解题思路

Sprint 4+（正式题库建设期）
─────────────────────────────────────────────────────────────
  1280 道正式题目陆续发布，自动触发向量化入库
```

#### 6.3.5 向量化触发流程

```python
# infrastructure/vector_store.py

COLLECTION_QUESTIONS  = "mesh_question_solutions"    # 题目解析库
COLLECTION_STRATEGIES = "mesh_five_power_strategies" # 五力策略文档库

async def embed_question(question_id: int):
    """
    触发时机：管理员将题目状态 draft → published 时，
    由 training_service.publish_question() 推送到 Celery Queue-A
    """
    question = await db.get(Question, question_id)

    # 拼接向量化文本（融合多个字段，提升检索质量）
    text = "\n".join(filter(None, [
        f"题目：{question.stem}",
        f"解析：{question.solution}",
        f"主训练力：{question.primary_power}",
        f"典型错误：{question.common_error}",
        f"洞察力训练点：{question.insight_point}",
        f"建构力训练点：{question.construct_point}",
    ]))

    embedding = await embedding_adapter.embed(text)  # 调用 DashScope API

    chroma_client.get_collection(COLLECTION_QUESTIONS).add(
        documents=[text],
        embeddings=[embedding],
        metadatas=[{
            "question_id":       question.id,
            "power_type":        question.primary_power,
            "difficulty":        question.difficulty,
            "knowledge_point_id": question.knowledge_point_id
        }],
        ids=[str(question.id)]
    )

    # 回写向量化状态到 PostgreSQL（source of truth）
    await db.update(Question, question_id,
                    embedding_status="completed",
                    embedded_at=datetime.now(timezone.utc))

# RAG 双路召回（answers 只从 ChromaDB 检索，原始内容从 PostgreSQL 读取）
async def rag_retrieve(question: Question, weak_powers: list[str]) -> dict:
    # 路径1：语义召回相似题（按薄弱五力过滤元数据）
    results1 = chroma_client.get_collection(COLLECTION_QUESTIONS).query(
        query_texts=[question.stem],
        n_results=3,
        where={"power_type": {"$in": weak_powers}}
    )
    # 路径2：召回对应五力策略文档
    results2 = chroma_client.get_collection(COLLECTION_STRATEGIES).query(
        query_texts=[f"{weak_powers[0]} 解题策略"],
        n_results=2
    )
    return {"solutions": results1["documents"], "strategies": results2["documents"]}
```

```python
from dashscope import TextEmbedding
import httpx

class EmbeddingAdapter:
    """

    维度：1536（与 ChromaDB collection 配置保持一致）

    async def embed(self, text: str) -> list[float]:
        provider = await redis.get("active_embedding_provider") or "dashscope"

        if provider == "dashscope":
            resp = TextEmbedding.call(
                model=TextEmbedding.Models.text_embedding_v2,
                input=text,
                api_key=settings.DASHSCOPE_API_KEY
            )
            return resp.output["embeddings"][0]["embedding"]

        elif provider == "openai":
            # OpenAI text-embedding-3-small，维度同样 1536

                    headers={"Authorization": f"Bearer {settings.OPENAI_API_KEY}"},
                    json={"model": "text-embedding-3-small", "input": text}
```

```sql
-- ─────────────────────────────────────────────────────────
-- ❌ 禁止在事务中执行耗时操作（如 LLM 调用）
-- ❌ 禁止 SELECT *，始终明确列名
-- ❌ 禁止在循环中执行数据库查询（N+1 问题）
-- ❌ 禁止删除已有迁移文件（可能导致生产数据丢失）
```

### 7.4 Git 工作流规范

```
分支策略：
  main          → 生产环境（受保护，禁止直接 push）
  develop       → 开发集成分支
  feature/*     → 功能分支（从 develop 分出，完成后 PR 合并回 develop）
  hotfix/*      → 紧急修复（从 main 分出，合并到 main + develop）

Commit 规范（Conventional Commits）：
  feat: 新功能
  fix: 修复 Bug
  docs: 文档更新
  refactor: 重构（不新增功能，不修复 Bug）
  test: 添加测试
  chore: 构建工具/依赖更新

示例：
  feat(training): 实现五力权重双档加权选题算法
  fix(auth): 修复 Token 刷新时未清除 Redis 黑名单的问题
  docs(api): 补充训练模块 API 文档
```

**健康检查端点实现（app/api/v1/health.py）：**

```python
from fastapi import APIRouter, Depends
from sqlalchemy.ext.asyncio import AsyncSession
from app.core.database import get_db
from app.core.redis_client import redis

router = APIRouter()

@router.get("/health")
async def health_check(db: AsyncSession = Depends(get_db)):
    """
    健康检查端点，供 Nginx / 负载均衡器探活使用
    检查：数据库连接、Redis连接
    返回 200 = 服务正常，返回 503 = 服务不可用
    """
    checks = {}
    try:
        await db.execute("SELECT 1")
        checks["database"] = "ok"
    except Exception:
        checks["database"] = "error"

    try:
        await redis.ping()
        checks["redis"] = "ok"
    except Exception:
        checks["redis"] = "error"

    is_healthy = all(v == "ok" for v in checks.values())
    return JSONResponse(
        content={"status": "healthy" if is_healthy else "unhealthy", "checks": checks},
        status_code=200 if is_healthy else 503
    )
```

### 9.3 数据备份策略

```
PostgreSQL 备份：
  方案：pg_dump 定时备份 + WAL 增量归档
  频率：每天 2:00 AM 全量备份，保留最近 7 天
  存储：备份文件上传 OSS（异地存储）
  命令：pg_dump -h localhost -U mesh mesh_prod | gzip > backup_$(date +%Y%m%d).sql.gz

Redis 备份：
  方案：开启 RDB 持久化（save 900 1，save 300 10，save 60 10000）
  AOF：开启 appendonly yes（确保数据不丢失）
  注意：Redis 数据为缓存/会话，可容忍短暂丢失；JWT 黑名单丢失最坏情况为已登出 Token 短暂可用

ChromaDB 备份：
  方案：定期打包 chroma_data 卷目录上传 OSS
  频率：每天 3:00 AM（与 PostgreSQL 备份错开）
  注意：向量数据可从题库重新生成，优先级低于数据库备份
```
