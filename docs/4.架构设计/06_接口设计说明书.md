## 1. 通用规范

### 1.1 基础信息

| 项目 | 说明 |
|------|------|
| Base URL（小程序） | `https://api.mesh-edu.com/api/v1` |
| Base URL（管理后台） | `https://api.mesh-edu.com/api/v1/admin` |
| 协议 | HTTPS |
| 数据格式 | `Content-Type: application/json; charset=UTF-8` |
| 字符集 | UTF-8 |
| 时间格式 | ISO 8601，`2026-08-30T10:00:00Z`（UTC） |

**小程序端 HTTP 方法约定：** 微信 `wx.request` 不支持 `PATCH`，小程序端所有「部分更新」请求以 `PUT` 发送；小程序端接口（`/profile/me`、`/assistant/message/{id}/rating`）同时接受 `PATCH` 与 `PUT`。小程序端 `DELETE` 请求的参数一律放查询字符串，不放请求体。

### 1.2 统一响应格式

所有接口的返回结构统一如下：

```json
{
  "status": "success",
  "code": 0,
  "msg": "操作成功",
  "data": {}
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `status` | string | 固定三值：`success`（成功）/ `fail`（业务失败）/ `error`（系统错误） |
| `code` | integer | 0 = 成功；非0 = 错误码（见 §1.4） |
| `msg` | string | 面向用户的提示信息（中文） |
| `data` | object/array/null | 业务数据体；成功时包含实际数据，失败时为 null |

**分页响应结构（列表接口）：**

```json
{
  "status": "success",
  "code": 0,
  "msg": "操作成功",
  "data": {
    "list": [],
    "total": 100,
    "has_more": true,
    "next_cursor": 80
  }
}
```

> 所有列表接口采用 **Keyset Pagination（游标分页）**，禁止使用 OFFSET 分页。

### 1.3 认证方式

```
Authorization: Bearer {access_token}
```

- **小程序端**：access_token 有效期 7 天，refresh_token 有效期 30 天，静默续期
- **管理后台**：access_token 有效期 8 小时，无 refresh_token，到期重新登录
- **Token 格式**：RS256 签名的 JWT

**无需 Token 的接口（白名单）：**
- `POST /api/v1/auth/wx-login`
- `POST /api/v1/auth/admin-login`
- `POST /api/v1/auth/sms/send`
- `POST /api/v1/user/reactivate`
- `GET /health`

**Token 黑名单中间件规范：**

所有受保护接口的认证流程：
1. 解析 `Authorization` Header 中的 `access_token`
2. 验证 JWT 签名和 `exp` 过期时间
3. 查询 Redis 黑名单：`GET blacklist:{jti}`（jti = JWT 唯一身份字段）
   - Key 存在 → 返回 `AUTH-001`（Token 已撤销）
   - Key 不存在 → 放行
4. 验证 `role` 字段权限后执行业务逻辑

**JWT Payload 规范：**
```json
{
  "jti": "uuid-唯一标识",
  "sub": "1001",
  "role": "STUDENT",
  "iat": 1693363200,
  "exp": 1693967200,
  "iss": "mesh-auth-service"
}
```

**Token 黑名单 Redis 存储：**
```
Key: blacklist:{jti}
Value: revoked
TTL: token 剩余有效期（自动过期，无需手动清理）
```

### 1.4 错误码规范

| 前缀 | 范围 | 模块 |
|------|------|------|
| `0` | — | 成功 |
| `AUTH-*` | 身份认证 | Token 过期/无效/权限不足 |
| `LOGIN-*` | 登录流程 | 密码错误/账号锁定 |
| `SMS-*` | 短信验证码 | 频率限制/验证码错误 |
| `REG-*` | 注册/绑定 | 手机号已注册/openid 已绑定 |
| `BIND-*` | 家长绑定 | 邀请码无效/绑定数量超限 |
| `TEST-*` | 五力测试 | 重测限制/画像生成 |
| `TRAIN-*` | 训练模块 | 无画像/题目不足 |
| `ASST-*` | 智能助教 | 轮数满/内容安全 |
| `ADMIN-*` | 管理后台 | 操作权限/配置错误 |
| `SYS-*` | 系统级 | AI 服务不可用/限流 |

**常用错误码：**

| 错误码 | HTTP状态 | 说明 | 用户提示 |
|--------|---------|------|---------|
| `AUTH-001` | 401 | Token 无效或已过期 | 请重新登录 |
| `AUTH-002` | 401 | Token 已在其他设备登录 | 账号已在其他设备登录 |
| `AUTH-003` | 403 | 权限不足 | 暂无权限 |
| `LOGIN-001` | 401 | 用户名/密码错误 | 账号或密码错误，剩余X次机会 |
| `LOGIN-002` | 403 | 账号已锁定 | 账号已锁定，请X分钟后重试 |
| `LOGIN-003` | 403 | 首次登录需改密 | 请先修改初始密码 |
| `SMS-001` | 429 | 发送太频繁 | 请60秒后再试 |
| `SMS-002` | 400 | 验证码错误 | 验证码错误，还可尝试X次 |
| `SMS-003` | 429 | 当日发送超限 | 今日验证码发送次数已达上限 |
| `REG-001` | 409 | 手机号已注册 | 该手机号已注册，请直接登录 |
| `REG-002` | 409 | openid 已绑定 | 当前微信已绑定账号 |
| `BIND-001` | 404 | 邀请码无效/已过期 | 邀请码不存在或已过期 |
| `BIND-002` | 409 | 绑定数量超限 | 最多绑定2位家长 |
| `TEST-001` | 409 | 重测间隔不足 | 距上次测试不足30天，暂不可重测 |
| `TRAIN-001` | 403 | 无五力画像 | 请先完成五力测试 |
| `TRAIN-002` | 400 | 知识点题目不足 | 该知识点题库建设中，暂不支持训练 |
| `ASST-001` | 400 | 对话轮数已满 | 本次对话已达上限，开启新对话继续？ |
| `ASST-002` | 400 | 内容安全拦截 | 该内容无法回复，换个方式试试？ |
| `SYS-001` | 503 | AI 服务暂不可用 | AI助手暂时休息，请稍后再试 |
| `SYS-002` | 429 | 接口限流 | 请求过于频繁，请稍后再试 |

## 2. 认证与账户模块

### 2.1 微信登录（学生/家长）

**接口：** `POST /api/v1/auth/wx-login`
**认证：** 无需 Token
**说明：** 微信授权，通过 code 换取 openid，判断是否已注册

**请求体：**
```json
{
  "code": "wx_auth_code_xxx",
  "user_info": {
    "nickname": "小明",
    "avatar_url": "https://..."
  }
}
```

**响应（新用户，需绑定手机号）：**
```json
{
  "status": "success",
  "code": 0,
  "msg": "授权成功，请绑定手机号",
  "data": {
    "is_new_user": true,
    "temp_token": "临时token，仅用于绑定手机号，有效期10分钟",
    "openid_hash": "用于前端临时存储，不含实际openid"
  }
}
```

**响应（已注册用户）：**
```json
{
  "status": "success",
  "code": 0,
  "msg": "登录成功",
  "data": {
    "is_new_user": false,
    "access_token": "eyJ...",
    "refresh_token": "eyJ...",
    "access_expires_in": 604800,
    "user_info": {
      "student_id": 1001,
      "nickname": "小明",
      "avatar_url": "https://...",
      "grade": "G9",
      "has_five_power_profile": true,
      "recommended_mode": "TRAIN_WEAKNESS"
    }
  }
}
```

**操作数据库：** 查询 `students`（by openid_hash），写入 `students`（新用户）

### 2.2 发送短信验证码

**接口：** `POST /api/v1/auth/sms/send`
**认证：** 无需 Token（新注册）或携带 temp_token
**说明：** 发送短信验证码，用于手机号绑定/登录/2FA

**请求体：**
```json
{
  "phone": "13800138000",
  "purpose": "BIND_PHONE"
}
```

`purpose` 可选值：`BIND_PHONE` / `LOGIN` / `TWO_FA`

**响应：**
```json
{
  "status": "success",
  "code": 0,
  "msg": "验证码已发送，5分钟内有效",
  "data": {
    "expire_seconds": 300,
    "cooldown_seconds": 60
  }
}
```

**业务约束：** 同号每60秒仅1次，每日最多10次
**操作数据库：** 写入 `sms_codes`

```json
{
  "status": "success",
  "code": 0,
  "msg": "绑定成功",

    "bind_method": "INVITE_CODE",
```

### 2.7b 家长绑定——方式二：家长主动发起（家长端）

> 家长输入学生手机号，系统向学生发送确认短信，学生确认后绑定生效。绑定请求有效期 24 小时。

**接口：** `POST /api/v1/user/parent-bind/request`
**认证：** 家长 Token（`user_type='PARENT'`）

**请求体：**
```json
{
  "student_phone": "13800000000"
}
```

**响应：**
```json
{
  "status": "success",
  "code": 0,
  "msg": "绑定申请已发送，等待学生确认",
  "data": {
    "binding_id": 102,
    "bind_status": "pending",
    "expires_at": "2026-09-13T10:00:00Z"
  }
}
```

**操作数据库：** 写 `parent_student_bindings`（`bind_method='PARENT_SELF'`，`bind_status='pending'`），发送短信通知至学生手机

---

### 2.7c 学生确认家长绑定申请（学生端）

> 学生收到短信通知后，在小程序中确认或拒绝家长的绑定请求。

**接口：** `POST /api/v1/user/parent-bind/confirm`
**认证：** 学生 Token（`user_type='STUDENT'`）

**请求体：**
```json
{
  "binding_id": 102,
  "action": "accept"
}
```

| `action` 值 | 说明 |
|------------|------|
| `accept` | 接受绑定，`bind_status` 变为 `active` |
| `reject` | 拒绝绑定，`bind_status` 变为 `rejected` |

**响应：**
```json
{
  "status": "success",
  "code": 0,
  "msg": "已接受绑定",
  "data": {
    "binding_id": 102,
    "bind_status": "active"
  }
}
```

**操作数据库：** 更新 `parent_student_bindings.bind_status`，`accept` 时置 `confirmed_at=NOW()`

### 2.8 管理员登录

**接口：** `POST /api/v1/admin/auth/login`
**认证：** 无需 Token

**请求体：**
```json
{
  "username": "admin001",
  "password": "plaintext_password"
}
```

**响应（成功）：**
```json
{
  "status": "success",
  "code": 0,
  "msg": "登录成功",
  "data": {
    "access_token": "eyJ...",
    "token_type": "bearer",
    "expires_in": 28800,
    "admin": {
      "id": 1,
      "username": "admin001",
      "display_name": "系统管理员",
      "role": "SUPER_ADMIN"
    }
  }
}
```

**业务规则：**
- 账号密码验证通过后直接返回 `access_token`，有效期8小时
- 连续失败5次锁定账号30分钟（LOGIN-002）
- `is_active=0` 返回 AUTH-003，`is_active=2` 返回 LOGIN-003（首次登录待激活）

**操作数据库：** 查询 `admin_users`（bcrypt比对），更新 `login_fail_count`，写入 `admin_audit_logs`

## 3. 五力认知测试模块

### 3.1 获取测试题卷

**接口：** `GET /api/v1/test/questions`
**认证：** 学生 Token
**说明：** 返回20道固定测试题（按 `display_order` 打散顺序），支持中断恢复

**响应：**
```json
{
  "status": "success",
  "code": 0,
  "msg": "操作成功",
  "data": {
    "session_id": 10001,
    "is_resumed": false,
    "current_question_index": 0,
    "total_questions": 20,
    "questions": [
      {
        "question_id": 5,
        "display_order": 1,
        "question_type": "STANDARD",
        "stem": "有一个封闭房间，里面放着完全相同的三杯热水...",
        "image_url": null,
        "options": [
          { "key": "A", "text": "三个杯子的水最后都会变凉" },
          { "key": "B", "text": "B和C都加了盖，但结果仍然不同" },
          { "key": "C", "text": "A杯没有毛巾" },
          { "key": "D", "text": "实验时间都是20分钟" }
        ],
        "reference_time_sec": 90
      }
    ]
  }
}
```

**业务说明：**
- 若已有 `in_progress` 状态的会话，直接返回该会话及当前进度（`is_resumed: true`）
- `question_type` 前台不展示，用于后端计分路径判断
- 不返回 `option_scores` 和 `option_force_weights`（防止学生猜测测的是什么）

**操作数据库：** 读 `cognitive_test_questions`，读/写 `test_sessions`

### 3.2 提交单题答案

**认证：** 学生 Token

```json
{
  "session_id": 10001,
  "question_id": 5,
  "question_index": 0,
  "selected_option": "B",
  "time_spent_sec": 45,
  "modify_count": 1

```

**响应：**
```json
{
  "status": "success",

    "remaining_count": 19,
```

**操作数据库：** 写/更新 `test_answer_records`，更新 `test_sessions.current_question_index`

- 检查 `five_power_profiles.is_latest=true`，无则返回 `TRAIN-001`
- 按知识点/单元/学期维度时，范围内题目不足5道返回 `TRAIN-002`
- 错题集维度时，该科目待攻克错题数=0返回 `TRAIN-003`
- 系统读取该维度 `training_dimension_configs.is_active=true` 配置，写入 `dimension_config_id`
- 错题集维度：按 `wrong_priority` 排序，按 `new_question_mix_ratio` 混入新题

**错误码：**

| 错误码 | 说明 |
|--------|------|
| `TRAIN-001` | 未完成五力测试，无法训练 |
| `TRAIN-002` | 范围内题目不足5道 |
| `TRAIN-003` | 错题集为空，该科目暂无待攻克错题 |
| `TRAIN-004` | 随机训练 / 错题集 / 收藏夹：学生资料缺年级或学期，请先补充 |
| `TRAIN-005` | 收藏夹训练：范围内暂无收藏题目 |

**操作数据库：** 读 `five_power_profiles`、`training_dimension_configs`（当前激活版本）、`questions`；ERROR_QUESTIONS额外读 `wrong_answer_records`；写 `training_sessions`


**智能训练（`SMART`）算法：**
- **信号**：五力得分；知识点 / 题型的薄弱度（近 120 天做题记录，半衰期 14 天的时间衰减 + 贝叶斯平滑，做得少时不会被判成 100% 错）；待攻克 / 已攻克的题；收藏；做题历史（避重复）；AI 助手聊天里的「近期困惑知识点」（大模型提取并缓存到 `student_learning_signals`，只存知识点 id、置信度和摘要，不存聊天原文，权重半衰期 7 天）
- **槽位**（默认 5 题，配比可在维度配置 `smart_params.slots` 调整）：弱项强化 60%、强项拓展 20%、复习与探索 20%；近期困惑的知识点至少占 1 题
- **打分与抽取**：每个槽位给每道题按各自用途打分（权重在 `smart_params.weights`），再按 `softmax(分数 / 温度)` 加权随机抽取，不取最高分，保证每次不一样；已选过的题型 / 知识点再选的概率降低（多样性）；没做过的题够用时完全排除最近做过的题
- **推荐理由 `reason.tag`**：`intent` 你提到的困惑 / `weak_kp` 薄弱知识点 / `pending` 待攻克巩固 / `type_weak` 题型强化 / `power` 弱项五力 / `strength` 强项拓展 / `due` 到期复习 / `fav` 收藏回顾 / `new` 新知识点探索 / `general` 综合推荐
- **没有聊天 / 大模型不可用**：只是少一类信号，其余信号照常出题；创建训练时不阻塞等待大模型，有缓存就用缓存，有新消息则后台刷新，只有从未分析过的第一次最多等 8 秒
- 每次分析聊天或完成训练后，会同步刷新后台「学生管理 → 摘要 → 学习信息摘要」（见 §9 学生 AI 提示词摘要）

### 5.2 提交单题答案

**接口：** `POST /api/v1/training/answer`
**认证：** 学生 Token

**请求体：**
```json
{
  "session_id": "uuid-training-xxx",
  "question_id": 5001,
  "question_index": 0,
  "student_answer": "400x - y = 3400",
  "student_answers": null,
  "final_answer": null,
  "time_spent_sec": 120,
  "hint_level_used": 0
}
```

**请求字段说明：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `student_answer` | string | 否 | 整段作答文本，写入答题记录和错题集用于展示。单选 `C`、多选 `CD`、判断 `对` / `错`；填空为各空用 `；` 连接；应用题为「解题过程 + 最终答案」拼接文本。**为空也可以提交**，按未作答判错 |
| `student_answers` | string[] | 否 | **填空题**按空分别作答的数组，传了就按数组逐空比对（答案里本身带逗号时不会被误拆）；不传则退回按 `,` `;` `，` `；` 拆分 `student_answer` |
| `final_answer` | string | 否 | **应用题**的「最终答案」一栏，传了就**只用它**判对错；不传则退回在 `student_answer` 整段里比对 |
| `hint_level_used` | int | 否 | 使用的最高提示级别，默认 0。**小程序答题页已取消「提示」功能，不再传该字段**（保持默认 0）；接口与数据库字段保留以兼容，后续如恢复提示功能再启用 |

**判题规则（服务端，纯规则比对，不调用大模型）：**

| 题型 | 判定 |
|------|------|
| 单选 | 作答（转大写）与标准答案选项字母相等 |
| 多选 | 提取作答中的 A–D 字母去重成集合，与标准答案集合相等（顺序、分隔符不限，多选少选均判错） |
| 判断 | 标准答案为「对」时作答须为 `true/对/正确/√/yes/1` 之一；为「错」时须为 `false/错/错误/×/no/0` 之一 |
| 填空 | 各空依次标准化后与标准答案列表**按顺序**完全相等 |
| 应用 | 标准答案 `final_answer` 中的所有数字都须出现在作答（优先 `final_answer` 字段）中；千分位逗号会被忽略（`10,600` 等同 `10600`） |
| 简答（预留） | 暂不支持自动判题，一律判错；后续接入大模型判分 |

**答案标准化（填空、应用比对前统一处理）：** 去除所有空白（含全角空格）、转小写、全角括号 / 减号 / 逗号 / 句号转半角；学生在手机上难以输入上标和乘号，下列写法统一成题库写法后再比对：`^9` → `⁹`（支持负指数，如 `10^-3` → `10⁻³`）；夹在数字 / 上标 / 右括号与数字 / 左括号之间的 `x` `*` `·` → `×`（字母变量如 `2x+1` 不受影响）。标准答案走同一标准化，故 `1.4x10^9`、`1.4*10^9`、`1.4×10⁹` 等价。

**响应：**
```json
{
  "status": "success",
  "code": 0,
  "msg": "提交成功",
  "data": {
    "answer_record_id": 80001,
    "is_correct": false,
    "rag_status": null,
    "proactive_trigger": false,
    "answered_count": 1,
    "remaining_count": 4,
    "can_complete": false,
    "already_answered": false,
    "student_answer": "400x - y = 3400"
  }
}
```

**业务说明：**
- `already_answered`：该题此前已提交过则为 `true`（本次没有新增记录），`student_answer` 为此前提交的作答；正常首次提交为 `false`
- `is_correct` 同步返回判题结果
- **答错时不再自动生成解析**：`rag_status` 恒为 `null`，参考解析改为学生在答题页点击「智能解答」时才通过 §5.3 按需调用大模型生成
- `proactive_trigger`：原设计为连续答错≥2次时触发 AI 主动介入悬浮条；**小程序答题页已取消该悬浮条**，服务端当前恒返回 `false`，前端不再使用该字段
- **已提交的答案不可覆盖修改**；前端答题卡跳回已答题时展示只读视图，不允许重新提交
- **同一会话的同一题只能提交一次**（数据库唯一约束 `(session_id, question_index)`）。重复提交（恢复了过期的中断快照、网络重试、连点）**不报错**，直接返回首次提交的结果：响应里 `already_answered = true`，`student_answer` 为首次提交的作答，`is_correct` 为首次的判题结果；不新增答题记录，也不重复写入错题集。并发的重复提交同样处理（捕获唯一约束冲突后回滚并返回已有结果）

**操作数据库：**
- 写 `training_answer_records`
- 答错时写 `wrong_answer_records`（review_status='unreview'）

### 5.3 智能解答（按需生成参考解析）

**接口：** `POST /api/v1/training/analysis`
**认证：** 学生 Token
**说明：** 学生**完成某题作答后**，在答题页点击「智能解答」按钮时才调用大模型，得出该题的参考解析。**不是答错后立即触发**；答对的题目同样可以点击查看。取代原先的 `GET /training/rag-status/{id}` 轮询接口和 `POST /training/rag-retry` 重试接口（两者已移除）。

**请求体：**
```json
{
  "session_id": "uuid-training-xxx",
  "question_id": 5001,
  "regenerate": false
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `session_id` | string | 是 | 训练会话 ID，必须是当前学生本人的会话 |
| `question_id` | int | 是 | 题目 ID；按 `session_id + question_id` 取该题最近一条答题记录，所以中断恢复后的已答题目也可以使用 |
| `regenerate` | boolean | 否 | 默认 `false`。`true` 时忽略已生成的解析，重新调用大模型（用于降级后「重新生成」） |

**响应：**
```json
{
  "status": "success",
  "code": 0,
  "msg": "操作成功",
  "data": {
    "status": "completed",
    "content": "【正确答案】……\n\n【解题思路】……",
    "static_solution": null,
    "cached": false
  }
}
```

| 字段 | 说明 |
|------|------|
| `status` | `completed`：大模型已生成，内容在 `content`；`degraded`：大模型不可用，已降级，内容在 `static_solution` |
| `content` | 大模型生成的参考解析（纯文本，用【】小标题分段，不含 Markdown），约 400 字以内 |
| `static_solution` | 降级时返回题库里的静态参考解析（`questions.solution`），没有则为「暂无参考解析」 |
| `cached` | `true` 表示直接返回此前已生成并保存的解析，没有再次调用大模型 |

**业务说明：**
- 提示词包含：题型、题目（单选 / 多选会先把选项从题干中拆出）、标准答案、题库参考解析和常见错误（如有）、学生作答、判题结果；要求按「正确答案 / 解题思路 / 你的作答 / 小结」结构输出，答错时指出错因，答对时给出补充思路
- 已生成过的解析保存在 `training_answer_records.rag_content`，再次请求直接返回缓存，不重复调用大模型
- 大模型调用整体超时 75 秒（小于小程序端 90 秒的请求超时）；未配置密钥、超时、网络或返回异常时**不返回 500**，降级返回 `status=degraded`，并把 `generation_status` 记为 `failed`，学生可点击「重新生成」重试
- 该接口为同步调用，耗时取决于大模型（通常数秒到数十秒），小程序端在解析卡片里显示「AI 正在生成解析」骨架屏

**错误码：**

| 错误码（HTTP） | 说明 |
|--------|------|
| 400 | 尚未作答该题（请先完成作答再使用智能解答） |
| 404 | 训练会话不存在（或不属于当前学生）/ 题目不存在 |

**操作数据库：** 读 `training_sessions`、`training_answer_records`、`questions`；生成成功时写 `training_answer_records`（`rag_content`、`rag_generated=true`、`generation_status='completed'`），降级时写 `generation_status='failed'`

### 5.7 查询训练中断记录（**v3.10.0 起小程序端不再调用，仅保留兼容**）

**接口：** `GET /api/v1/training/interrupt`
**认证：** 学生 Token

**说明：** 查询当前学生在指定科目+训练维度下是否存在未完成的中断记录。学生在"选择训练维度"页面进入后调用，若存在中断则提示恢复。

**与数据库对齐（服务端处理）：**
- 中断记录只在学生点「退出并保存」时写入。如果学生恢复后继续作答、又没有再正常退出（直接关闭小程序），记录里的 `answers_snapshot` 就是过期的。因此查询时服务端**以数据库里该会话的真实答题记录为准**补全 / 覆盖 `answers_snapshot`，并把 `current_question_index` 顺延到第一道没答的题（全部答完则停在最后一题，只读查看），避免恢复后对已答过的题再提交一次
- 如果该会话已不存在或已不是进行中（已完成 / 已放弃），这条中断记录没有恢复意义，服务端会**直接删除并返回 `has_interrupt = false`**

**Query Params：**

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `subject_code` | string | 是 | 科目代码，如 `MATH` |
| `training_dimension` | string | 是 | 训练维度，如 `KNOWLEDGE_POINT` |

**响应（有中断记录）：**
```json

  "code": 0,
  "msg": "存在未完成的训练",

      "subject_code": "MATH",
      "training_dimension": "KNOWLEDGE_POINT",
      "scope_label": "二元一次方程组应用题",
      "current_question_index": 2,
      "total_questions": 5,
      "answered_count": 2,
      "interrupted_at": "2026-09-26T10:30:00Z"

}
```

**响应（无中断记录）：**
```json
{
  "status": "success",
  "code": 0,
  "msg": "暂无未完成的训练",
  "data": {
    "has_interrupt": false,
    "interrupt": null
  }
}
```

**操作数据库：** 读 `training_interrupts`（按 student_id + subject_code + training_dimension）

**点任意一级进入训练：** `POST /training/session`，`training_dimension = FAVORITES`，`subject_code`，可选 `chapter_id`、`knowledge_point_id` 限定范围。题从范围内的收藏题里按题型 / 难度比例抽取（默认 5 题），尽量避开最近做过的题；没有收藏题返回 `TRAIN-005`（暂无收藏题目）。收藏夹训练里答错仍归入待攻克，答对不改变待攻克 / 已攻克状态（只有错题集训练里答对才攻克）。

**取消收藏：** 在收藏夹训练里取消收藏，本轮训练照常继续，题目只是从收藏夹里去掉，下次不会再抽到。

**操作数据库：** 表 `question_favorites`（`student_id` + `question_id` 唯一）；`training_sessions.training_dimension` 与 `training_dimension_configs.dimension` 的取值新增 `FAVORITES`。

## 7. 智能助教模块

> **v3.12.0 改版：** AI 助教接入大模型，实现启发策略选择与切换、理解突破识别与成就感反馈、沉默模式、重新生成、滚动摘要、快捷提问、图片提问。单一永久会话：没有「新对话 / 结束对话 / 历史记录」，原 `POST /session/{id}/end`、`GET /sessions` 已移除。

### 7.1 获取或创建永久对话会话

**接口：** `POST /api/v1/assistant/session`（无请求体）
**说明：** 学生只有一个 `free_chat` 会话，有则复用，没有则新建并写入一条个性化开场白（根据薄弱知识点 / 近期困惑生成的模板，不调用大模型）。
**响应：** `{session_id, session_mode, is_new, silence}`，`silence` 为沉默模式当前是否有效（超过 `chat_silence_timeout_min` 分钟自动解除）。

### 7.2 发送消息

**接口：** `POST /api/v1/assistant/message`
**请求体：** `{session_id, content, image_url?}`，`content` 0~500 字（无图片时必须有内容，有图片时可以为空）

**处理流程：**
1. 校验：空内容 `ASST-004`；超过 500 字 `ASST-003`；关键词内容安全拦截 `ASST-002`（不入库、不进大模型）
2. 学生说「我自己想」等 → 进入沉默模式，只回一句确认（不调用大模型），事件 `silence_mode`
3. 沉默中学生说「你来说 / 给我提示」等 → 解除沉默
4. 含「我明白了 / 我懂了」等关键词 → 大模型确认是否真正的理解突破：是 → 生成成就感反馈消息（`is_aha_trigger=true`，≤120 字），`aha_count+1`，事件 `aha_moment`，该策略有效性 +1 次 `effective`；否 → 走普通回复
5. 普通回复：选启发策略（见下）→ 组装提示词（系统提示词 + 本轮策略 + 学习状态 + 老师 / 系统记录的个人洞察 + 最近 12 条消息）→ 调用大模型 → 回复截断到 ≤400 字
6. 学生消息和 AI 回复一起写入 `ai_chat_messages`（大模型失败时两条都不入库，返回 `ASST-005`，学生可原样重发）；记录 `ai_token_usage_log`

**响应：** `{message_id, role, content, is_aha_trigger, rating, created_at, student_message_id, silence}`

**启发策略选择：**
- 每个策略有「有效性得分」（0~100，基准 50；点赞 +6、点踩 -8、触发理解突破 +10、被判无效切走 -4）
- 选择得分 = 该学生该策略的有效性得分 + 适用学生最弱一力 +8 + 默认优先级微调
- 同一策略连续用满 2 次且没有理解突破 → 自动切换到有效性最高的其它策略，写 `ai_strategy_events`（`strategy_switch`，原策略 `ineffective_count+1`）；首次选择写 `strategy_start`

### 7.3 获取历史消息（分页）

**接口：** `GET /api/v1/assistant/messages?session_id=&before_id=&limit=30`
**说明：** 不传 `before_id` 取最新一页；传了取这条之前更早的一页（向上翻页）。响应 `{messages: [...正序], has_more}`。

### 7.4 对 AI 消息评分

**接口：** `PATCH /api/v1/assistant/message/{message_id}/rating`（小程序端用 `PUT` 发送，两种方法等价，见 §1.1）
**请求体：** `{rating: "like" | "dislike"}`；可改选，计数随之调整，并更新该消息所用策略的有效性得分。

### 7.5 重新生成

**接口：** `POST /api/v1/assistant/message/{message_id}/regenerate?session_id=`
**说明：** 对不满意的 AI 回复，换一种策略重新生成，**替换原消息内容**（评分清空）；成就感消息不可重新生成（`ASST-007`）。

### 7.6 解除沉默

**接口：** `POST /api/v1/assistant/silence/resume?session_id=`

### 7.7 快捷提问

**接口：** `GET /api/v1/assistant/suggestions`
**说明：** 对话为空时展示。依据学生的近期困惑、薄弱知识点、待攻克错题、最弱一力生成 3~4 条，不足用通用问题补齐。响应 `{suggestions: [...]}`。

### 7.8 图片提问

图片**不单独解析**：学生选好图片后先上传，再和问题一起发给 AI 助教，由助教（多模态大模型）直接看图回答。

**上传：** `POST /api/v1/assistant/image`，请求体 `{image_base64, media_type}`（jpg / png / webp，≤6MB）。服务端按**文件头**判断真实类型（不信任客户端声明），保存到 `uploads/assistant/<随机UUID>.<ext>`（目录已被 .gitignore 忽略，以 `/uploads` 静态路径对外提供），返回 `{image_url: "/uploads/assistant/xxxx.png"}`。

**随消息发送：** `POST /assistant/message` 的请求体新增 `image_url`（上传返回的路径，必须是本服务的上传目录里存在的文件，否则 `ASST-006`），`content` 有图片时可以为空（为空时用默认提问「请帮我看看这张图片里的问题，先别急着给答案，一步步引导我思考」）。图片作为 `ai_chat_messages.image_url` 存库，历史消息里返回 `image_url`。

**给大模型：** 本条消息以多模态格式（图片 + 文字）发送，图片读成 data URL 随请求发出（大模型访问不到本机地址）；较早消息里的图片只留「[图片]」标记，不重复发送；重新生成时会带上对应的图片。配置的模型不接受图片输入时返回 `ASST-008`（「当前 AI 模型暂不支持看图」），不假装识别。

### 7.11 退出时更新摘要

**接口：** `POST /api/v1/assistant/digest`（无请求体，静默调用）
**说明：** 小程序在**退出助教页**（切到别的 Tab / 进入别的页面，`onHide`）和**小程序退到后台**（`App.onHide`）时调用。服务端**立即返回** `{scheduled}`，有新聊天内容时在后台更新对话摘要（§7.9）、个人洞察（§7.10）和聊天困惑信号，更新由服务端完成，小程序随后被系统挂起也不影响。

**触发点汇总：**
1. 退出助教页 / 小程序退到后台（本接口）。
2. 下次进入助教页（`POST /assistant/session`）时补一次，防止退出时那次请求丢了（网络断开、小程序被系统直接回收）。
3. 兜底：聊天里累积够 10 条新消息，不等退出就更新。

**条件与防抖：** 距上次更新后至少有一问一答（≥2 条新消息、其中有学生消息）才更新；同一学生两次更新之间至少间隔 60 秒（兜底路径不受此限）；同一学生同一时间只跑一个更新。没有会话、没有新消息、离上次太近时什么都不做（`scheduled=false`），所以客户端可以放心在每次退出时调用。小程序端只在这次启动里聊过天时才调用。

### 7.10 个人洞察闭环

「个人洞察」是一段总结概括的文字（不分条目），描述「这个学生是什么样的人」，给 AI 助教看：兴趣爱好、学习 / 类比偏好、近期状态、重要生活事件、家庭情况、学习态度。

**存储（`student_ai_prompt_summaries`）：**
- `insight_admin_text`：**管理员确认的部分**——管理员在摘要页保存的整段文字。AI **永远不改写**它。
- `insight_ai_text`：**AI 补充的部分**——AI 根据聊天概括出的、管理员文字里还没有的内容（≤200 字）。AI 只更新这一块。
- `personal_insight` = 管理员部分 + 换行 + AI 部分。页面展示、助教提示词读取的都是它（≤700 字，超长只截 AI 部分，管理员部分原样保留）。

**规则：**
1. **AI 更新**（触发点见 §7.11）：把「管理员确认的部分 + 此前的 AI 补充 + 学生最近说的话」交给大模型，要求只输出更新后的 **AI 补充**（一段话，不重复管理员已有信息，与管理员确认的内容有出入时以管理员为准）。**不存聊天原文**，不写姓名、号码、学校、住址。
2. **管理员修改**：管理员在摘要页改完点保存，保存的**整段文字（包含页面上看到的 AI 补充）都成为新的「管理员确认的部分」**，AI 补充清空；之后 AI 只在它后面补充。想让某条 AI 补充消失，删掉后保存即可（AI 以后如果又从聊天里概括出类似内容，可能再次补充）。
3. **管理员写的内容不会被 AI 更新弄丢**：这是存储结构上的保证（AI 根本不写管理员部分），不依赖大模型是否听话。并发时，AI 写入前会重新读取最新的管理员部分再拼接，管理员刚保存的内容不会被 AI 用旧数据覆盖。
4. **采用规则**：AI 补充没变化、含长数字串、或已有较长补充（≥40 字）被缩得很短（疑似丢信息）、或已有补充却输出空时，不采用，保留原样。
5. **敏感**：涉及情绪、家庭、生活事件的句子，句首加「【敏感】」。提示词要求助教**只用来调整语气和节奏，不直接向学生提起、也不复述**。
6. **使用**：助教每次回复前读取 `personal_insight`，放进系统提示词的「老师 / 系统记录的个人特点」。后台摘要页的「Prompt 预览」展示的就是助教实际使用的提示词（不含每轮变化的启发策略）。
7. 更新失败（大模型不可用 / 返回异常）只记日志，不影响聊天；没有聊天时就不会有 AI 补充。

### 7.9 对话摘要（滚动）

永久会话没有「结束」，所以按消息累积滚动生成：每累积 10 条新消息，后台用「已有摘要 + 新对话」更新 `ai_chat_sessions.session_summary`（≤100 字，第三人称，不含学生原话），并记录 `summary_message_id`。摘要更新后同步刷新智能训练的「聊天困惑信号」和后台「学生管理 → 摘要 → 学习信息摘要」。

**错误码：** `ASST-002` 内容安全拦截；`ASST-003` 消息超过 500 字；`ASST-004` 消息为空；`ASST-005` AI 暂时无法回复（大模型未配置 / 超时 / 报错，**不再返回固定的假回复**）；`ASST-006` 图片无效 / 过大 / 已失效；`ASST-007` 该消息不可重新生成；`ASST-008` 当前 AI 模型不支持看图。

#### 9.1.3 触发模型分析

**接口：** `POST /api/v1/admin/questions/{question_id}/analyze`

**权限：** `SUPER_ADMIN`

**说明：** 对 `draft` 状态的题目触发大模型分析，题目状态变为 `analyzing`。分析为异步执行，前端轮询状态接口（9.1.4）等待完成。

**请求体：** 无（或空 `{}`）

**响应：**
```json
{
  "status": "success",
  "code": 0,
  "msg": "模型分析已触发，请稍后刷新查看结果",
  "data": {
    "question_id": 5100,
    "status": "analyzing",
    "analysis_round": 1
  }
}
```

**业务说明：**
- 题目状态由 `draft` 变为 `analyzing`
- 系统向大模型提交 Prompt：包含题干内容、系统角色描述、期望输出格式（含科目/年级/章节/知识点/难度/解析/五力等）
- 若题目存在 `rejection_reason`（驳回意见），该意见自动携带至大模型 Prompt 中（提示模型本次为驳回后重新分析）
- 大模型返回结构化结果后，系统写入 `question_analyses` 表，题目状态更新为 `pending_review`，`rejection_reason` 自动清空
- 分析失败（超时/模型错误）时状态回退为 `draft`，记录失败原因

**操作数据库：** 更新 `questions.status='analyzing'`，触发 Celery Queue-B（大模型分析任务）

#### 9.1.10 批量操作（后端批量接口）

> **v3.2.0 调整：** 题目列表支持复选框多选，批量模型分析、批量发布、批量删除均由**后端批量接口**一次性处理。前端只提交勾选的题目 ID 列表，**不再循环调用单题接口**（勾选 100 条不再产生 100 次请求）。资格校验、状态流转、并发与限流控制全部由后端负责。
> 本节取代 v2.3.0 的「前端串行编排」方案。
> **v3.3.0 新增：** 训练题管理页支持复选框多选，新增批量启用（9.1.10.4）、批量停用（9.1.10.5）两个后端批量接口，约定同上。

**批量接口的共同约定（9.1.10.1 ~ 9.1.10.5 均适用）**

| 项目 | 说明 |
|------|------|
| 权限 | `SUPER_ADMIN` |
| 请求体 | `{ "question_ids": [5007, 5004, ...] }`，数组元素为题目 ID（整数） |
| 数量限制 | 单次 **1 ~ 200** 条；重复 ID 由后端去重（`total` 以去重后数量为准） |
| 处理语义 | **逐条独立处理，部分成功**：单条不满足条件或失败不影响其他题目；整体请求只要通过入参校验即返回 HTTP 200，结果在 `data.items` 中逐条给出 |
| 结果枚举 | `result`：`success`（已处理）/ `skipped`（状态不符，未处理）/ `failed`（处理出错） |
| 原因码 | `reason_code`（`skipped` / `failed` 时返回）：`STATUS_NOT_ALLOWED` 状态不符；`NOT_FOUND` 题目不存在或已删除；`ANALYSIS_INCOMPLETE` 分析数据不完整（仅批量发布）；`STATE_UNCHANGED` 题目已处于目标启用状态，无需变更（仅批量启用 / 停用）；`SYSTEM_ERROR` 系统异常 |
| 响应汇总字段 | `total`（去重后总数）、`success_count`、`skipped_count`、`failed_count`（三者之和 = `total`） |
| 审计日志 | 每次批量调用写 **1 条** `admin_audit_logs` 汇总记录（操作类型、题目 ID 列表、各结果数量），不逐题写多条 |
| 前端预校验 | 前端可依据列表中已有的 `status` 提前判断：勾选项中不存在可处理状态时，直接提示、不发请求；存在时弹窗确认后再调用接口。**前端预校验仅为交互优化，最终以后端校验为准** |

**批量接口通用错误码：**

| code | HTTP | 说明 |
|------|------|------|
| `QBATCH-001` | 400 | `question_ids` 为空，或包含非整数 / 非法值 |
| `QBATCH-002` | 400 | 单次提交超过 200 条 |
| `AUTH-003` | 403 | 权限不足（非 `SUPER_ADMIN`） |

##### 9.1.10.1 批量模型分析

**接口：** `POST /api/v1/admin/questions/batch-analyze`

**说明：** 对勾选的 `draft` 状态题目批量触发大模型分析。分析为异步执行：接口在题目状态置为 `analyzing`、任务入队后立即返回，不等待分析完成。

**请求体：**
```json
{ "question_ids": [5007, 5006, 5004] }
```

**响应：**
```json
{
  "status": "success",
  "code": 0,
  "msg": "批量分析任务已提交",
  "data": {
    "total": 3,
    "success_count": 2,
    "skipped_count": 1,
    "failed_count": 0,
    "items": [
      { "question_id": 5007, "result": "success", "status": "analyzing" },
      { "question_id": 5006, "result": "skipped", "reason_code": "STATUS_NOT_ALLOWED", "reason": "仅草稿状态的题目可以触发分析", "status": "pending_review" },
      { "question_id": 5004, "result": "success", "status": "analyzing" }
    ]
  }
}
```

**业务说明：**
- 资格过滤：仅 `draft` 状态参与；`analyzing`、`pending_review`、`published`、`archived` 返回 `skipped`
- 每道通过校验的题目：状态 `draft → analyzing`，**批量**投递 Celery Queue-B（大模型分析任务），一题一个任务；与单题接口（9.1.3）的分析逻辑、Prompt 构造（含 `rejection_reason`）、失败回退规则完全一致
- **限流与并发由后端负责**：Queue-B 按配置的并发度消费任务，前端不再做请求间隔控制
- 分析完成后题目状态变为 `pending_review`，前端通过列表 / 详情接口刷新查看

**操作数据库：** 批量更新 `questions.status='analyzing'`，批量投递 Queue-B，写 1 条 `admin_audit_logs`

##### 9.1.10.2 批量发布

**接口：** `POST /api/v1/admin/questions/batch-publish`

**说明：** 对勾选的 `pending_review`（待审核）状态题目，**直接使用各题最新一次大模型分析结果**批量发布，等同于列表「发布」按钮（快速发布）逐题执行的效果，但在一次请求内由后端完成。管理员需要修改分析字段的题目，应进入「审核结果」页面（9.1.5）单题发布。

**请求体：**
```json
{ "question_ids": [5006, 5002, 5001] }
```

**响应：**
```json
{
  "status": "success",
  "code": 0,
  "msg": "批量发布完成",
  "data": {
    "total": 3,
    "success_count": 1,
    "skipped_count": 1,
    "failed_count": 1,
    "items": [
      { "question_id": 5006, "result": "success", "status": "published", "embedding_status": "pending" },
      { "question_id": 5002, "result": "skipped", "reason_code": "STATUS_NOT_ALLOWED", "reason": "仅待审核状态的题目可以发布", "status": "draft" },
      { "question_id": 5001, "result": "failed", "reason_code": "ANALYSIS_INCOMPLETE", "reason": "分析数据不完整（缺少科目 / 年级），请进入审核页补充后再发布", "status": "pending_review" }
    ]
  }
}
```

**业务说明：**
- 资格过滤：仅 `pending_review` 参与；其他状态返回 `skipped`
- 发布字段取自该题 `question_analyses` 最新一轮的 `ai_*` 字段（归属体系、难度、解析、五力权重、训练思路、迁移方向、题目类型、答案等），写入规则与 9.1.5 一致；`primary_power` 由系统取 `five_power_weights` 最大值对应维度
- 完整性校验：`ai_subject_id`、`ai_grade_id` 缺失，或五力权重不合法（非 0~10 整数 / 合计 ≠ 10），该题 `failed` 且 `reason_code=ANALYSIS_INCOMPLETE`，**状态保持 `pending_review` 不变**
- **每道题独立事务**：单题发布失败只回滚该题，已成功发布的题目不受影响
- 发布成功的题目**批量**投递 Celery Queue-A（题目向量化入库 ChromaDB），`embedding_status=pending`；五级知识树节点计数随之更新
- 发布后题目转至「训练题管理」模块

**操作数据库：** 批量更新 `questions`（写入全部确认字段），批量投递 Queue-A，写 1 条 `admin_audit_logs`

##### 9.1.10.4 批量启用

**接口：** `POST /api/v1/admin/questions/batch-activate`

**说明：** 对勾选的**已停用**训练题（`status='published'` 且 `is_active=false`）批量启用，题目重新加入小程序端练习抽题。语义与单题启用（9.1.8，`PATCH /questions/{question_id}/active`）一致，区别仅在于一次请求内由后端完成。

**请求体：**
```json
{ "question_ids": [5003, 5001, 5009] }
```

**响应：**
```json
{
  "status": "success",
  "code": 0,
  "msg": "批量启用完成",
  "data": {
    "total": 3,
    "success_count": 1,
    "skipped_count": 2,
    "failed_count": 0,
    "items": [
      { "question_id": 5003, "result": "success", "status": "published", "is_active": true },
      { "question_id": 5001, "result": "skipped", "reason_code": "STATE_UNCHANGED", "reason": "题目已处于启用状态", "status": "published", "is_active": true },
      { "question_id": 5009, "result": "skipped", "reason_code": "STATUS_NOT_ALLOWED", "reason": "仅已发布的题目可以启用", "status": "draft", "is_active": true }
    ]
  }
}
```

**业务说明：**
- 资格过滤，按以下顺序判定：
  1. 题目不存在或已删除 → `skipped`，`reason_code=NOT_FOUND`
  2. `status != 'published'` → `skipped`，`reason_code=STATUS_NOT_ALLOWED`
  3. `is_active` 已为 `true` → `skipped`，`reason_code=STATE_UNCHANGED`（幂等，不视为失败）
  4. 其余 → 置 `is_active=true`，`result=success`
- 仅更新 `questions.is_active`，**不改变 `status`**，题目数据与 `deleted_at` 不受影响
- 每道题独立处理，部分成功；单题异常返回 `failed`（`SYSTEM_ERROR`），不影响其他题目
- 启用成功的题目，ChromaDB 对应向量批量标记 `is_active=true`，重新参与训练推荐

**操作数据库：** 批量更新 `questions.is_active=true`，ChromaDB 向量批量标记 `is_active=true`，写 1 条 `admin_audit_logs`（操作类型 `BATCH_ACTIVATE_QUESTION`）

##### 9.1.10.5 批量停用

**接口：** `POST /api/v1/admin/questions/batch-deactivate`

**说明：** 对勾选的**已启用**训练题（`status='published'` 且 `is_active=true`）批量停用，题目从小程序端练习抽题中移除。语义与单题停用（9.1.7）一致。

**请求体：**
```json
{ "question_ids": [5001, 5002] }
```

**响应：** 结构同 9.1.10.4，`msg` 为「批量停用完成」，成功项返回 `"is_active": false`；已停用的题目返回 `skipped` + `STATE_UNCHANGED`（`reason`：「题目已处于停用状态」）。

**业务说明：**
- 资格过滤顺序同 9.1.10.4：`NOT_FOUND` → `STATUS_NOT_ALLOWED`（非 `published`，`reason`：「仅已发布的题目可以停用」）→ `STATE_UNCHANGED`（`is_active` 已为 `false`）→ 置 `is_active=false`

- 停用成功的题目，ChromaDB 对应向量批量标记 `is_active=false`，不再参与训练推荐
- 每道题独立处理，部分成功

**操作数据库：** 批量更新 `questions.is_active=false`，ChromaDB 向量批量标记 `is_active=false`，写 1 条 `admin_audit_logs`（操作类型 `BATCH_DEACTIVATE_QUESTION`）

**前端交互约定（与 `07_产品设计说明书.md` §9.1.1 对应）：**

```
勾选题目 → 点击「批量发布 / 批量分析」
  ├─ 未勾选任何题目            → 提示「请先勾选需要…的题目」，不发请求
  ├─ 勾选项中无可处理状态      → 提示「所选题目中不包含 X 状态的题目…」，不发请求
  └─ 存在可处理状态            → 弹窗确认（显示可处理数 / 将跳过数）
                                    └─ 确认 → 一次调用批量接口 → 按 data 汇总提示：
                                         success_count 全部成功      → 成功提示
                                         存在 skipped / failed       → 警告提示，列出各自数量
```

**训练题管理页（批量启用 / 停用）的前端交互约定（与 `07_产品设计说明书.md` §10 对应）：**

```
勾选题目 → 点击「批量启用 / 批量停用」
  ├─ 未勾选任何题目            → 提示「请先勾选需要…的题目」，不发请求
  ├─ 勾选超过 200 条           → 提示「单次最多… 200 道题目」，不发请求
  ├─ 勾选项中无可处理题目      → 提示「所选题目均已处于启用/停用状态」，不发请求
  │    （启用：可处理 = is_active=false；停用：可处理 = is_active=true）
  └─ 存在可处理题目            → 弹窗确认（显示可处理数 / 将跳过数）
                                    └─ 确认 → 一次调用批量接口 → 按 data 汇总提示（规则同上）
```

> 前端仅依据列表中已有的 `is_active` 做预校验与提示，**最终以后端校验为准**；训练题管理列表仅展示 `status='published'` 的题目，故前端无需处理 `STATUS_NOT_ALLOWED`，该原因码作为后端兜底（如页面数据过期）。

**设计说明：** 批量请求次数恒为 **1 次**，与勾选数量无关；原前端串行方案（每条 1 次、发布每条 2 次请求）在勾选量较大时耗时线性增长、中途中断会出现不可见的部分完成状态，且无法由后端统一做限流与审计，故改为后端批量接口。

#### 9.3.4 变更题目状态（启用 / 停用）

**接口：** `PATCH /api/v1/admin/cognitive-questions/{id}/status`

**权限：** `SUPER_ADMIN`

**请求体：**
```json
{
  "status": "published"
}
```

**`status` 合法值：**

| 值 | 说明 | 前置状态要求 |
|----|------|------------|
| `published` | 启用题目（含停用后编辑的题目） | 来源状态为 `archived` |
| `archived` | 停用题目 | 来源状态为 `published` |

**响应（成功）：**
```json
{
  "status": "success",
  "code": 0,
  "msg": "题目已启用",
  "data": {
    "id": 25,
    "status": "published",
    "published_count": 19,
    "test_available": false
  }
}
```

**业务规则：**
- **启用（含启用）：**
  - 当前已启用数 ≥ 20 时拒绝启用，返回 `COGQ-001` 错误

- **停用：** 始终允许停用；停用后题目进入可编辑且可删除的 `archived` 状态；停用后若已启用数 < 10，返回体附带 `"test_available": false` 警告

**错误码：**

| 错误码 | HTTP | 说明 | 端侧提示 |
|--------|------|------|---------|
| `COGQ-001` | 400 | 已启用题目已达20道上限 | 「已启用题目已达上限（20/20），请先停用一道题目后再启用」 |
| `COGQ-002` | 400 | 非法状态转换 | 「当前题目状态不支持此操作」 |
| `COGQ-003` | 404 | 题目不存在 | 「题目不存在或已删除」 |

**操作数据库：** 更新 `cognitive_test_questions.status`，写入 `admin_audit_logs`

#### 9.3.6 批量启用测试题

**接口：** `POST /api/v1/admin/cognitive-questions/batch-activate`

**权限：** `SUPER_ADMIN`

**说明：** 对勾选的**已停用**测试题（`status='archived'`）批量启用，等同于列表操作列「启用」逐题执行的效果（9.3.4 `status=published`），但在一次请求内由后端完成。测试题的「启用状态」由 `status` 表示：**已启用 = `published`，已停用 = `archived`**，测试题只有这两个状态。

**请求体：**
```json
{ "question_ids": [9, 12, 15, 17] }
```

**批量约定（与 9.1.10 一致，此处列出本接口的差异）：**

| 项目 | 说明 |
|------|------|
| 数量限制 | 单次 **1 ~ 200** 条；重复 ID 由后端去重（`total` 以去重后数量为准） |
| 处理语义 | 逐条独立处理，部分成功；整体请求通过入参校验即返回 HTTP 200，结果在 `data.items` 中逐条给出 |
| 结果枚举 | `result`：`success` / `skipped`（未处理）/ `failed`（处理出错） |
| 汇总字段 | `total`、`success_count`、`skipped_count`、`failed_count`（三者之和 = `total`）；另附 `published_count`（处理后已启用总数）、`test_available`（已启用数 ≥ 10） |
| 审计日志 | 每次批量调用写 **1 条** `admin_audit_logs` 汇总记录，不逐题写多条 |

**响应：**
```json
{
  "status": "success",
  "code": 0,
  "msg": "批量启用完成",
  "data": {
    "total": 4,
    "success_count": 1,
    "skipped_count": 3,
    "failed_count": 0,
    "published_count": 20,
    "test_available": true,
    "items": [
      { "question_id": 9,  "result": "success", "status": "published" },
      { "question_id": 12, "result": "skipped", "reason_code": "STATE_UNCHANGED", "reason": "题目已处于启用状态", "status": "published" },
      { "question_id": 15, "result": "skipped", "reason_code": "NOT_FOUND", "reason": "题目不存在或已删除" },
      { "question_id": 17, "result": "skipped", "reason_code": "PUBLISH_LIMIT_REACHED", "reason": "已启用题目已达上限（20/20）", "status": "archived" }
    ]
  }
}
```

**业务说明：**
- 资格判定，按以下顺序：
  1. 题目不存在 → `skipped`，`reason_code=NOT_FOUND`
  2. `status='published'` → `skipped`，`reason_code=STATE_UNCHANGED`（幂等，不视为失败）
  3. `status='archived'` → 进入上限判定
  4. 其他取值（历史脏数据，如遗留 `draft`）→ `skipped`，`reason_code=STATUS_NOT_ALLOWED`（兜底）
- **启用上限（20 道）：** 与 9.3.4 的 `COGQ-001` 规则一致。后端先读取当前已启用数，可启用名额 = `20 - 已启用数`；符合条件的 `archived` 题目**按请求中 `question_ids` 的提交顺序**依次占用名额，名额用尽后其余题目返回 `skipped` + `PUBLISH_LIMIT_REACHED`，**不整体失败**；名额判定与状态变更在同一事务内完成，避免并发超发
- 启用成功：`status` 变为 `published`，写 `updated_by`；启用不影响历史测试成绩（历史会话依赖快照）
- 每道题独立处理；单题异常返回 `failed`（`SYSTEM_ERROR`），不影响其他题目

**原因码：** `NOT_FOUND` 题目不存在；`STATUS_NOT_ALLOWED` 状态不符；`STATE_UNCHANGED` 已处于目标状态；`PUBLISH_LIMIT_REACHED` 已启用数达上限；`SYSTEM_ERROR` 系统异常。

**错误码：**

| code | HTTP | 说明 |
|------|------|------|
| `CBATCH-001` | 400 | `question_ids` 为空，或包含非整数 / 非法值 |
| `CBATCH-002` | 400 | 单次提交超过 200 条 |
| `AUTH-003` | 403 | 权限不足（非 `SUPER_ADMIN`） |

**操作数据库：** 批量更新 `cognitive_test_questions.status='published'`、`updated_by`，写 1 条 `admin_audit_logs`（操作类型 `BATCH_ACTIVATE_COGNITIVE_QUESTION`）

#### 9.3.7 批量停用测试题

**接口：** `POST /api/v1/admin/cognitive-questions/batch-deactivate`

**权限：** `SUPER_ADMIN`

**说明：** 对勾选的**已启用**测试题（`status='published'`）批量停用为 `archived`，等同于列表操作列「停用」逐题执行的效果（9.3.4 `status=archived`）。

**请求体：** `{ "question_ids": [1, 2, 3] }`

**响应：** 结构同 9.3.6，`msg` 为「批量停用完成」，成功项返回 `"status": "archived"`。

**业务说明：**
- 资格判定，按以下顺序：`NOT_FOUND` → `status='archived'` 返回 `skipped` + `STATE_UNCHANGED`（`reason`：「题目已处于停用状态」）→ 其他取值（历史脏数据）返回 `skipped` + `STATUS_NOT_ALLOWED` → `status='published'` 置为 `archived`

- 每道题独立处理，部分成功

**操作数据库：** 批量更新 `cognitive_test_questions.status='archived'`、`updated_by`，写 1 条 `admin_audit_logs`（操作类型 `BATCH_DEACTIVATE_COGNITIVE_QUESTION`）

**前端交互约定（与 `07_产品设计说明书.md` §11.3.1 对应）：**

```
勾选题目 → 点击「批量启用 / 批量停用」
  ├─ 未勾选任何题目            → 提示「请先勾选需要…的题目」，不发请求
  ├─ 勾选超过 200 条           → 提示「单次最多… 200 道题目」，不发请求
  ├─ 勾选项中无可处理题目      → 提示原因，不发请求
  │    （启用：可处理 = 已停用；停用：可处理 = 已启用）
  ├─ 批量启用且已启用数已达 20 → 提示「已启用题目已达上限（20/20），请先停用部分题目」，不发请求
  └─ 存在可处理题目            → 弹窗确认（可处理数 / 将跳过数；启用时若可处理数超过剩余名额，
                                    额外说明「仅按勾选顺序启用前 N 道」）
                                    └─ 确认 → 一次调用批量接口 → 按 data 汇总提示：
                                         全部成功                → 成功提示
                                         存在 skipped / failed   → 警告提示，列出各自数量
                                         test_available=false     → 追加提示「已启用不足 10 道，测试功能已暂停」
```

> 前端仅依据列表中已有的 `status` 与已启用计数做预校验与提示，**最终以后端校验为准**。

### 10.6 统一分页方式说明

接口设计统一使用 **Keyset Pagination（游标分页）**，`05_数据库设计说明书.md` 所有高频列表查询索引已按此优化（包含时间字段的倒序索引），无需修改，补充设计原因说明：

> 使用 `before_id` + `LIMIT` 代替 `OFFSET` + `LIMIT`，避免大数据量下 OFFSET 性能退化，且支持实时数据一致性。
